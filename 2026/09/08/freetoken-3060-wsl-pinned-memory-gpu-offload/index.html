3060 6GB 跑 FreeToken：从锁页 OOM 到 5 token/s，我最后改了哪里

发表于 2026-09-08 分类于 LLM 阅读次数：
接着前两篇 FreeToken 文章，这次在自己的 RTX 3060 Laptop 6GB 上实跑 Qwen3.6-35B-A3B：从 Windows、WSL 的启动问题，到恢复 GPU 专家计算，再逐项测试缓存和异步传输能带来多少提速。

前面写了两篇 FreeToken，一篇看8GB 显存为什么能跑 35B MoE，另一篇继续看缩到 6GB 后该怎么配置、会遇到哪些限制。原理和别人的成功案例看了一些，接下来还是想在自己的机器上实际跑一下。

我手里正好有一台 RTX 3060 Laptop 的笔记本，6GB 显存、32GB 内存。那就用它来试试前面讨论的 Qwen3.6-35B-A3B-NVFP4，看看 FreeToken 到底能不能把这个模型带起来。

不过这次不太想停在“启动成功，能回一句话”这一步。既然已经折腾了，就想再往下看看：能不能让这张 3060 真正参与专家计算，把剩下的显存利用起来，在不反复 OOM 的前提下，尽量多挤一点生成速度出来？

本来以为主要工作是安装、准备模型，再调几个启动参数。实际从 Windows 客户端试到 WSL，先后碰到了转换失败、权重加载异常和内存不足。后来总算能回答了，专家计算却大部分落在 CPU 上。这才有了后面那个问题：GPU 呢？模型能跑是一回事，有没有用好这台机器又是另一回事。

所以这篇接着前两篇，记录我在这台 3060 上真正跑通、再继续调性能的过程。哪些设置解决了问题，哪些调整没有用，以及最后为什么没有继续把显存填满，都放在一起说。

最后跑到了什么程度

先放一下这轮折腾的结果：最终保留了 896 个专家缓存槽位，加异步 staging。固定提示词短测的生成速度，从本地同步版本的 3.56 token/s 提到 5.17 token/s，也能正常完成中文、算术和分块输入测试。

这不是已经找到了 3060 的性能上限，而是这次测过的几组配置里，我愿意留下来继续用的一组。再加缓存还有一点提升，但会进一步压缩显存余量，后面会把数字展开。

这里的约 45% 提升，比较的是两个都带本地兼容补丁的配置，不是和官方 main 比出来的。官方原路径在这套环境里会先卡在锁页内存分配上。先记住这个区别，下面从机器和失败的位置说起。

Windows 客户端之前显示的版本是 v0.2.0-beta.17，这次 WSL 服务接口报告的引擎版本是 0.1.2。它们不是同一个版本号，排查时别混着写。

这也不是“6GB 显存就够了”的案例。专家库仍然占用 16.93 GiB 系统内存，还有框架、分词器和各种缓冲。机器有 32GB 物理内存；不能据此保证 16GB 内存也能跑。

都叫 OOM，失败的位置却不一样

前面遇到过 Windows 模型转换失败、加载存储异常，换到 WSL 后又遇到 OOM。后来真正拦住 GPU offload 的报错是：

这里申请的是 CPU 侧可被 CUDA 使用的锁页内存，并不等于显存已经用完。继续减 KV cache，或者把 WSL swap 从一个数字改成另一个数字，都不一定能解决这条路径。

我分别试了两种分配方式：先分配 mmap 再注册的 cudaHostRegister，以及直接分配锁页缓冲的 cudaHostAlloc。这台机器上，两次都在累计约 1 GiB 后失败。

这个数字只能说明本机当时的观察结果。它不是“所有 WSL 都只能锁 1GB 内存”的规则。NVIDIA 的 CUDA on WSL 文档确实列出了锁页系统内存可用量受限的问题，但没有给所有配置规定同一个 1GB 上限。

Windows 分页文件也曾被关闭。重新配置后，之前的虚拟机异常退出没有在后续测试中复现；但这没有让大规模 CUDA 锁页申请成功。系统提交空间、WSL swap、锁页内存和显存，需要分别排查。

还有一个容易误判的地方：服务长时间空闲以后，日志里的周期吞吐可能把等待时间算进去。前面曾出现过极低的周期数字，不能拿它当纯 CPU 的可比基准。本文的速度统一从客户端流式请求计时得到。

绕开整库锁页，让 GPU 继续算专家

FreeToken 原来的 GPU offload 路径，需要让专家源数据成为 GPU 可以读取的锁页内存。缓存缺失时，再把需要的专家搬进显存槽位。

我的库有 16.93 GiB。既然整库锁页在这台机器上走不通，就把它留在普通系统内存里，只给搬运中的那一小批专家准备锁页缓冲：

这里的 CPU 负责收集、复制字节，不负责专家矩阵乘法。所有 40 层的专家计算仍走 CUDA。显存放不下全部专家，所以这些权重按需进入 GPU 缓存，而不是 35B 权重常驻显存。

实现上，每组 bank 一次暂存最多 8 个专家。使用字节视图，是为了完整保留 NVFP4 的打包数据以及 FP8、FP16 缩放值，不在搬运过程中重新量化。超过 8 个 miss 就分块处理。

这条路径也有代价：多了一次 CPU 收集，仍然要过 PCIe；为了处理动态专家索引，会有 CPU/GPU 同步。因此当前明确关闭 CUDA graphs，也关闭 overlapping prefill。它是一条兼容性退路，还不能说是通用最快实现。

先让同步版本正确，再减少等待

第一版每次复制都用阻塞 H2D。好处是容易确认缓冲区什么时候能重用；坏处是每层的多组权重都要等一次。

后面改成异步传输时，并不是把 non_blocking=False 随手换成 True 就结束了。CPU 如果提前覆盖锁页缓冲，GPU 可能读到下一批专家的数据，结果会悄悄变错。

当前补丁依赖同一个 CUDA stream 的执行顺序：读取下一次 miss 数量时等待前面的工作完成；同一次调用中，若超过 8 个专家，需要再次写同一块 host buffer，就先等待该块完成传输。之后的 cache scatter 和专家计算也保持在同一个 stream 上。

我检查了空 miss、离散槽位、超过 8 个 miss、整层 prefill，以及连续 20 次缓冲区复用；打包字节、FP8 和 FP16 都做了逐字节对照。这些检查比看到一句正常中文更重要。

显存从 74% 用到 84%，再往上收益不大

每档配置使用同一个模型和提示词，关闭思考，温度为 0。先做一次 32-token 上限的预热，再做两次 96-token 上限的请求，每次接口报告 95 个输出 token。

我最后留了 896。1024 加异步只再快约 1.2%，却多占了 216 MiB。每档只有两次短测，这点差距也可能落在波动里，不值得为它把余量压得更紧。

固定提示词测试时，896 配置占用 5158 MiB，约为 6 GiB 的 84%。后面跑了中文和其他输入形状，显存升到 5248 MiB，剩余 747 MiB。框架缓冲会变化，不能把一次截图当成永久上限。

显存使用率也不是 GPU 算力利用率。测试期间采样的 GPU 平均忙碌比例，基线约 35.5%，优化版约 36.5%，其中包含 prefill 和等待。速度提高了，不代表计算单元已经满载。

这段修改能贡献给官方吗

我已经把最初能跑的版本和优化版分别存档。准备贡献时，最需要避免的是把整个排障目录直接丢成一个 PR：里面还有旧的转换、权重加载和页面缓存调整，它们不该混进这个改动。

官方仓库的 issue #55已有锁页池不足的讨论。我的补充点是：在锁页预算很小、CPU 专家计算又不理想时，用有界 staging 保留 GPU 专家计算。这值得拿具体复现和补丁去讨论，但还不能说官方已经接收。

按 贡献指南，还需要核对最新 main、补上失败前后测试，并说明性能对照到底比较了什么。AI 辅助写过代码，也应该如实说明。作者得能解释缓冲区的生命周期，而不是只转发一句“测试通过”。

整理本文时，我下载检查了 main 快照 af71ba43206e124f5ff6419b47ee36c6e9981078。引擎已经调整过锁页预算，提取后的旧补丁不能整份直接应用；缓存和日志部分的文本应用检查通过。这只是源码检查，不是最新 main 的整机回归。 现有可用服务没有为这次整理而被替换。

对我来说，这次最有用的结果不是把显存数字填满，而是终于分清了：哪一次 OOM 是显存不够，哪一次是锁页申请失败，以及每增加一段等待究竟换来了什么。
