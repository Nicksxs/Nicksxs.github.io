DeepSeek V4.1 Flash 为什么更省：从读一段日志，到写出答案

发表于 2026-09-11 分类于 LLM 阅读次数：
接着 3060 跑 FreeToken 的实操，从分析故障日志的例子出发，逐步理解 DeepSeek V4.1 Flash 的输入输出分工、缓存共享与压缩、局部重放、Engram 和推测解码，也算清激活参数、缓存与整机内存不是同一本账。

前几天在自己的 3060 笔记本上折腾 FreeToken，我花了不少时间盯着显存占用。只有 6GB，模型又大，很容易顺着直觉想：是不是再多挤一点显存，就能快一点？

后来发现，要看的不止这个数字。专家权重放在哪里、什么时候搬进显存、CPU 和 GPU 有没有互相等待，都可能影响最终速度。有时候不是显卡算不动，而是数据还没准备好。

所以这次看到 DeepSeek V4.1 Flash 发布，我先没急着看排行榜。更想顺着上次的问题往前想一步：我们在运行阶段努力减少浪费，那么模型从设计开始，能不能就少算一点、少搬一点、少存一点？

这篇不打算把一串新缩写摆出来挨个翻译。我们拿一个场景慢慢走：给模型一大段故障日志，请它解释连接超时。沿着日志进去、答案出来的过程，看看计算和存储分别花在哪里，又有哪些工作可以省。

资料范围：截至 2026 年 9 月 11 日，本文核对了官方发布说明、模型卡、公开参考推理代码及相关原始研究。V4.1 技术报告的 PDF 下载在本次环境中失败，因此不把本文称为对该报告的逐页复现。下文日志、动画和小数字例子均为教学示意，没有在本机部署 V4.1 Flash，也没有测量它的实际速度。

先把桌上的两样东西分开

假设你正在排查一个 Java 服务。你打开日志，看到大量正常请求，中间夹着几次超时。你想让模型帮忙找关联，于是把日志和问题一起发过去。

这时可以把模型的工作台想成两部分。

一部分是工具书：里面是已经学到的知识和处理问题的方法。它对应模型权重。这次换一份日志，不会因此重新训练整套权重。

另一部分是本次排查的工作笔记：刚读过什么、哪些中间结果后面还用得上。它对应请求相关的状态，其中很重要的一类就是 KV Cache。

工具书很大，工作笔记也可能很大。两者都要找地方放，但它们不是同一个东西。

这个区别看似简单，却能避免不少误解：缩小工作笔记，不意味着工具书也缩小了；同时接待更多请求，通常又会增加各自需要的工作空间。即使某些相同前缀可以共享，也不能把所有请求都当成同一份笔记。

日志不是以整篇文章为单位送进去的

文字会先变成 token 序列。token 是分词器处理的单位，并不严格等于一个汉字、一个英文单词或一个字节。日志中的时间、标点、路径，也会参与分词。

模型处理整段输入、建立后续生成所需状态的阶段，通常叫 prefill，预填充。接着逐步生成新 token，叫 decode，解码。

“逐步”很重要。输入已经给定，其中不少计算可以批量进行；而生成时，下一个位置依赖已经生成的内容，存在顺序约束。这里说的是工作方式，不是承诺输入一定比输出快多少。

于是第一个问题自然来了：读很长的材料，只写很短的答案，两种工作有没有必要采用完全一样的计算安排？

第一笔账：读材料和写答案，重新分工

想象你要根据一百页日志写半页分析。最终答案虽然短，但为了准备它，前面的材料都需要处理。

如果某些状态可以由前一道工序直接提供，就不必让后一道工序对全部输入重复建立一遍。这里省的不是“日志不读了”，而是准备状态的路径发生变化。

这次 DeepSeek 将主干组织为前后二十层的 Causal Encoder-Decoder，因果编码器—解码器。后半段的全局 KV 来自前半段最终表示的投影，而不是每一层都从自己的隐藏状态独立生成。官方给出的激活参数量是输入阶段 8B、生成阶段 16B。模型卡

可以暂时把“投影”理解成：把前半段已经算好的表示，转换成后半段需要的格式。它不是把日志转成一段人工可读的摘要，更不是先问一个小模型，再把文字回答交给另一个大模型。

“因果”也不表示模型真的懂得了故障的因果关系。这里主要描述信息可见性的约束：一个位置不能任意利用未来还没出现的 token。

共享全局缓存、让输入阶段提前结束部分计算，并不是没有前人工作的方向。可以对照 YOCO 原论文：它把生成全局状态和使用这些状态分开。这是理解设计动机的参照，不代表两套模型的具体实现完全相同。

8B 为什么不是“小模型”的证明

MoE 可以拥有很多专家，却只让一部分专家参与当前 token 的计算。它更像一家有很多科室的医院，这次会诊只请了其中几位医生。来了几位，不等于医院一共只有几位。

官方说明的 552B 是主干参数口径；模型卡还单独列出了 196B 的 Engram 参数。不能拿输入激活的 8B 当成全部需要存储的参数，也不宜把主干数字和下载页面自动汇总的数字混为一谈。发布说明、模型卡

记住两句话即可：

  • 有多少参数，关系到模型容量和存储负担。
  • 一次激活多少参数，反映计算方面的重要信息，却不能单独决定速度。

如果专家数据来不及送到计算单元，少激活也未必换来理想速度。这一点，恰好能接回上次 FreeToken 的实际经历。

第二笔账：已经读过的内容，后面怎么找回来

现在模型开始组织回答。它想解释“连接超时”，需要回看前面的信息。

问题是，日志里可能有很多内容并不相关。一次正常心跳、一条请求完成记录，和错误前的重试配置，重要程度显然不同。

注意力机制就是让当前位置利用其他位置的信息。粗略说，当前查询 Q 会和历史位置的 K 做匹配，再用匹配结果组合 V 中的信息。

可以把 K 理解成线索，把 V 理解成取回来使用的内容。但请给这个比喻加一道边界：真正保存的是向量，不是模型写下的一列关键词和一段摘要。 它也不是像数据库索引一样保证精确命中某条事实。

KV Cache 保存这些可复用的中间状态，避免后面每生成一点内容，都把历史的 K、V 全部重算。

只看重点，还不是全部答案

如果前面有很多位置，逐个做完整注意力计算会很贵。稀疏注意力先选出一部分值得看的位置，再重点处理。

不过，挑位置本身也要计算。假设第一位排查者已经找到几段相关日志，第二位接手时还从第一行开始找，虽然每个人最后都只精读几段，前面的筛选工作还是重复了。

所以接下来可以分开问：

  1. 已经准备好的资料，下一层能不能共用？
  2. 已经挑出的相关位置，下一层能不能接着用？

这正是 CSA2，Compressed Sparse Attention 2 里值得关注的部分。参考代码用来源层来管理共享的 KV 和索引，并提供候选预筛选相关配置。官方参考实现

为了理解分工，可以把三种模式记成三张交接条：

模式接手时主要沿用什么大白话
Full本组需要的新缓存和选择在这里建立我准备资料，也找位置
Reindex已有缓存；重新选择关注位置资料不重抄，但我有自己的问题
Reuse已有缓存和相关位置选择这次连前面的页码也接着用

Full 是这套模式的名字，不等于传统的全量密集注意力。 共享部分状态，也不等于后面的层被删除了，或各层输出完全相同。

分层索引还能把后续筛选限制在候选范围中。先圈出可能相关的部分，后续再细找，减少反复面向全部上下文的筛选。它同样有取舍：选得好不好，需要训练和质量评估；“计算变少”本身不能证明“一个重要细节都没有漏”。

第三笔账：笔记共用了，每个数字还能不能更省地方

到这里，我们讨论的都是少准备几份、少查几遍。还可以换一个方向：每份缓存本身能不能写得更紧凑？

计算机保存浮点数要用比特。量化就是用较少的表示空间，近似保存原本更精细的数字。

举个与实际模型格式无关的小例子：原来需要区分 1.001、1.002、1.003，现在一种粗一点的刻度可能把它们放到附近同一个档位。空间变小了，但信息不可能原样无损保留。

因此不能把 FP4 理解成“给文件做一次 ZIP 压缩”。它涉及精度取舍和缩放信息，训练与推理内核也要配套。直接把旧模型的缓存强制截短，不等于得到同样的模型表现。

V4.1 Flash 使用 FP4 主 KV 缓存。官方公布的组合结果，是全局 KV 每 token 890 字节，相对 V4 Flash 约缩至四分之一。这里同时包含架构和共享等设计的作用，不能全部归功于 FP4。官方模型卡

如果用十进制的一百万 token 举例：

这是从官方每 token 数字推导的全局 KV 理论账面量，不是实测显存。

为什么我特意写这句？因为很容易顺手得出“百万上下文只要不到 1GB 显存”的结论，接着再想“我的小显卡也行”。

这张账单还没有加上权重、局部状态、运行时缓冲、内存分配粒度以及其他请求。实际系统还可能做分片、共享或额外预留。只算一栏算得很准确，也不能拿它代替总账。

还可以再想一步：如果你真的把一百万 token 填满，缓存占得下只是第一关。读入要多久、能否找到分散的信息、回答是否正确，是另外几关。

第四笔账：只管最近一段的状态，为什么一直放硬盘

并非所有注意力都需要回看整个历史。有一类只关注最近的窗口，叫滑动窗口注意力，SWA。

像排查日志时，你一边保留全局线索，一边盯着错误附近的连续记录。全局线索和局部工作状态，保存价值并不一样。

假设局部状态过期了，但需要的原始片段还在。与其把所有局部状态长久保存，不如需要时只重放最近那个有限窗口，补回继续工作所需的状态。

这就是 SWA Bounded Replay 的直观动机。官方将持久缓存降至前代约八分之一，与局部 KV 不再需要持久保存到 SSD 联系起来。模型卡

注意它不是“删掉旧日志”，也不是“重算整个历史”。它改变的是局部计算状态的存储与恢复方式。有限重放具体怎样衔接缓存、误差和边界，需要看实现与验证，不能单凭比喻推断逐位等价。

这属于典型的时间与空间交换：恢复时多做一些计算，换长期存储和传输的减少。如果每次都频繁恢复，收益又可能不同。

因此官方的“HBM 约四分之一”和“SSD 约八分之一”不能互换。HBM 是加速器上的高带宽内存；SSD 是固态存储。它们都可能放缓存，但访问方式和成本差异很大。发布说明

到这里停一下：几种省法到底省了什么

你在解决的问题这里讨论的办法不能顺手推出的结论
输入很多，准备状态太贵输入输出分工、复用编码状态输入完全不用算了
各层反复准备和筛选历史共享 KV、复用索引、候选筛选后面的层完全相同
中间数字太占地方低比特缓存精度无损、全部内存都同比减少
局部状态长期存储太贵有限窗口重放恢复零成本、日志被删除

你不必背住所有缩写。只要遇到“提速”“省显存”时，愿意追问一句具体少了哪份工作，基本就不会被几个大数字带走。

还有一种重复工作：熟悉的模式为什么也要重新重建

前面讲的是这次日志产生的缓存。现在换一种东西：训练中学到的记忆。

我们看到一个熟悉的固定表达，往往能直接认出来，不必每次都从头拆解。模型能不能也有一条更直接的查找路径，把一部分网络计算留给真正需要组合和推理的地方？

Engram 提供的是条件记忆：根据局部 token 组合做确定性查找，取出训练得到的表示，再通过上下文相关的处理融入计算。它与 MoE 的按需计算形成互补。Engram 原论文

这里有三种“记忆”值得分开：

  • KV Cache：这次请求的计算状态。
  • Engram：训练得到的、可按条件访问的模型记忆。
  • 外部检索：从模型之外的文档或数据库获取资料。

Engram 不等于联网搜索，也不是把完整事实逐条存进一个能直接阅读的问答表。它并不保证查一次就能解决问题。

它的表仍然要存储，访问仍然需要带宽。如果按“每次只查一点”就认为整个表不占空间，又回到了激活量与总容量混淆的问题。

这项研究早于本次模型发布。理解这层关系，比把每个出现在新模型里的名字都叫作“全新发明”更有帮助。

最后一笔账：答案为什么一定得等那么多次

日志读完，相关内容也找好了，接下来是输出。

通常生成下一个 token，要依赖前面的结果。即便每一步已经比较省，只要串行轮次多，等待还是会累积。

推测解码换了一个做法：先用较便宜的草稿计算准备多个候选，再由主模型验证。能接受的部分推进，不能接受的部分修正。

这并不是“让小模型代替大模型回答”。严格的推测采样还需要处理接受概率和拒绝后的分布修正，目的在于加速而不任意改变目标采样分布。动画中的绿格、红格只用来表示接受与退回，不是完整数学算法。推测解码原论文

V4.1 的 DSpark 使用半自回归草稿和基于置信度的验证安排；相关实现也能看到草稿头和置信度头的区分。vLLM DSpark 实现说明

收益取决于草稿是否容易被接受，以及草稿、验证、状态管理各自要花多少时间。一个任务中经常猜错，另一个任务中经常猜对，两者不会有同样的收益。

因此我不会在没有实际测量时写“必定快两倍”。也不要把推测解码路线写成本次才出现的新概念。

为什么还要说训练和多模态

少算一点，并不会自动让答案更可靠。改变计算路径之后，还需要让模型学会使用它，并通过任务验证。

官方说明，这个版本从预训练阶段就联合处理视觉和文字表示；后训练基本流程仍是 SFT、RL、在线策略蒸馏，主要扩展在任务与数据环境，而非替换成一套新的后训练算法。模型卡

理解这些概念不必从缩写开始。先看别人怎样完成任务，再自己做、接受反馈，然后把能力进一步传递或巩固，是一个粗略的学习类比。真实训练还涉及奖励是否可信、环境是否足够多样、任务是否污染评测集等问题，远比类比复杂。

至于 Single-Pass mHC，它涉及模型内部多条信息流如何混合。可以先把残差连接理解成“在新计算之外保留已有信息的通道”；通道变多，表达可能更丰富，也更需要控制混合的稳定性和执行开销。mHC 原论文

这里我只把它放回正确的位置，不仅凭名字展开未核实的内核步骤，更不把所有能力提升都归因于它。

普通使用者最后该看什么

对写代码、查日志、处理文档的人来说，与其只记参数表，不如拿自己经常做的任务记录四件事：

  1. 答案是否可验证。 故障原因有没有日志证据，建议能不能执行，还是看起来很像那么回事。
  2. 总共等了多久。 首字等待和后续生成要分开，Agent 还要算工具调用与重试。
  3. 任务到底花了多少钱。 不只看单价，还要看输入输出量、缓存命中和重复尝试。
  4. 长上下文究竟有没有用上。 能接收一份长文档，与稳定利用其中的信息，不是同一能力。

这些是建议的验证方法，不是本文已经测出的结论。本文没有新建付费 DeepSeek 调用，也没有将这套超大模型重新装到 3060 上。

官方基准测试还涉及推理强度、工具框架和上下文设置。比较时要把条件一起看，而不是截下一行分数就宣布所有任务全面胜出。

回到开始的那段日志

现在再看日志进去、答案出来的过程，就不只剩一个“大模型在思考”的黑箱了。
