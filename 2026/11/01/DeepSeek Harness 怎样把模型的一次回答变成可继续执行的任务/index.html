模型知道 BigDecimal.equals() 会区分 scale（小数位数），不代表一个 Agent 就能修好 Java 项目。它还得读对文件、执行修改、跑完测试，把失败结果带进下一次请求；执行到一半断了，还得知道哪一步能重试。

DeepSeek Harness 值得拆的部分，就藏在这些动作之间。下面沿着一个测试修复任务，读它如何把流式输出、工具执行、事件日志和下一次模型请求接起来。重点看四个实现选择，以及省掉它们会出什么问题。

本文为静态源码分析，固定在官方仓库提交 ce7073d。Java 项目、调用参数和测试输出是讲解用的示例，没有实际运行；标明“源码”的 TypeScript 片段来自该提交。

最朴素的实现会在流里识别到工具名和一段看似合法的 JSON，就立即调用函数。这既可能执行尚未确定的参数，也难以回答“到底是哪次模型输出触发了这个操作”。这里先形成正式消息，再启动执行，留下了明确的因果顺序。代价是要等本次流结束，不能靠提前猜测调用来抢那一点延迟。

不过，“先进入 Session 日志”不要读成“每次执行前都已刷盘”。持久化是另外的能力，append 和持久化屏障 flush 也有区别；这段代码没有承诺工具执行前逐次刷盘。持久化接入契约

参数字符串先由批处理代码解析；如果不是合法 JSON，会保留原字符串交给工具管线形成参数诊断，而不是用 eval 当代码执行。prepare 处理执行前策略、审批与拒绝条件，dispatch 进入工具实现，complete 完成结果处理。调度器允许工具主体重叠运行，但执行前处理和结果提交仍按模型给出的顺序推进。执行器分派、执行管线

这不是把所有调用丢给 Promise.all。executionMode() 只有在工具的 isConcurrencySafe(arguments) 明确返回 true 时，才允许并行。没有声明、返回其他值或判断抛错，都会归为独占调用。独占调用相当于一道屏障：前面的并行组收完，它单独执行完，后面的调用再开始。**调度器信任工具的并发声明，不会替工具分析两个业务操作是否冲突。**因此也不能因为两条命令看起来都是读操作，就断言当前 bash 调用自动并行。并发分类源码

替换边界也不能随便选。假如删掉 assistant 的测试调用，却留下它的 tool 结果，模型协议中的配对关系就断了。实现会检查区间两端的工具调用与结果是否平衡，拒绝切断配对。只按字符数删掉前半截聊天记录，恰恰容易犯这个错。区间检查

对本例，一个有用摘要应保留“金额忽略 scale”“原实现使用 equals”“已改为 compareTo”“哪次测试实际通过”等事实；这是摘要应该达到的效果，不是实现能自动保证的正确性。压缩节约上下文，却引入信息损失，而且不会顺便解决原始日志的存储体积。

中断恢复必须区分还没开始和结果已经无法确认

最能看出这套日志价值的时刻，是改文件或跑测试时进程断了。

ToolCallRecovery 跟踪三类事实：assistant 提出了哪个调用、调度器是否记录了 tool/call、是否已有配对的 tool/result。下面讨论同一会话中断后的恢复；fork 分支的提示还有额外语义。恢复时不会把“没有结果”统统解释成“工具没执行”。源码中决定错误类型的几行是：

这里的 started 是日志记录意义上的开始。settlement.start() 发生在 pipeline.prepare() 之前，所以出现 tool/call 甚至不保证已经进入工具主体。它只能把恢复范围分成两种：

  1. **保存的历史中没有开始记录。**恢复补上 TOOL_NOT_STARTED，中断恢复提示是仍有需要时重试。这是基于已保存日志作出的分类，不能越过前述刷盘窗口，推断外部世界绝对没有发生操作。

  2. **记录了开始，但没有结果。**恢复补上 TOOL_OUTCOME_UNKNOWN，说明无法从保存的历史确认结果。源码给模型的指引是：只读或幂等操作才考虑直接重试；可能有副作用时先核对外部状态，不要盲目重试。

如果已经有配对结果，就不再补一份。未闭合的 step 和 turn 也会补上结束事件，使后续历史保持完整。恢复状态判定、调用开始的实际位置

放回 Java 例子：若 Money.java 已改好，但修改工具来不及记录结果，恢复后应先读文件或检查 diff，再决定是否重做补丁。若测试命令结果丢失，要按测试是否有外部副作用判断能否重跑；不能因为名字叫“测试”就默认无副作用。

这个设计接受一个分布式执行中的现实：文件系统变化、数据库提交与 Session 日志并不天然属于同一个事务。“外部操作已成功，结果记录尚未保存”这段窗口客观存在。Harness 能留下明确的未知状态，让下一步作保守判断；它不能仅凭日志保证所有外部操作恰好执行一次。

修复闭环的关键是把已发生和未知分清楚

整个金额修复过程最终回到同一条链：模型提出动作，Harness 形成消息并记录；执行器调度工具，记录实际结果；下一次请求从日志的可见索引重建，模型继续判断。流被截断时不执行半成品调用，工具并发时不打乱结果顺序，历史过长时替换可见内容，中断时保留“结果未知”而不伪造成功。

这四处实现值得借鉴，因为它们分别回答了一个可检查的问题：**何时允许执行，结果按什么顺序提交，下次模型到底看到什么，中断后究竟知道多少。**把这些问题讲清楚，一个 Agent 才不只是能连续调用模型，而是能交代每一步为什么发生、发生到哪里。
