第 17 讲｜Agent 安全与工具执行边界

用威胁建模、权限、隔离、审批与可重跑的状态检查理解 Agent 安全。

  • LESSONS

课程索引 · 下载 Markdown

2026 年 11 月 18 日 · Agent 安全与防护。 Stanford 课件

一段会被人看到的错误说明，和一段会被工具执行的错误说明，后果差别很大。预约助手说错了设备的归还时间，用户可以纠正。助手如果能操作台账，同一个误解可能把别人的预约取消。做这类系统时，先写清工具读得到什么、可以改变什么，以及由谁决定批准。

先把事故和滥用落到具体后果

课件从系统自身事故、外部攻击、滥用、目标错配与串谋来组织风险。做事故复盘，可以再问四个问题。系统是不是优化了错误的目标？它是否执行了不可逆或超出范围的动作？长任务推进中有没有丢掉原始约束？它是否把失败报告成了成功？例如用「一小时成功关闭的预约数」衡量效率，会让系统偏好能快关的工单。若它删了被误判为重复的记录，问题在评分目标、工具授权和取消策略都有可能存在。只换提示词难以区分是哪一层出错。 Stanford 课件

外部攻击通常从可读取内容进入。模型会处理以自然语言写成的网页、文档和工具输出，这些内容可能试图改变它的任务判断。直接提示和间接提示的区别在入口。用户输入直接到达会话，第三方文字通过检索、邮件或文件到达会话。数据源真实存在，也不意味着其中所有文字都可信。就算来源字段表明它取自登记系统，附加的自由文本仍然只是一段数据。宿主应用应以结构化的授权规则决定下一步动作。 Stanford 课件 · Agent 安全设计模式

滥用从预期使用者或已获权限的系统出发。一个人获准读取自己的领用记录后，也许会要求按全院范围找到所有借用者的私人联系方式。能够完成某项任务的 API 客户端，仍要接受租户、身份、目的和记录范围的检查。多 Agent 系统则多一层传播。即使 A 只有查看权限，如果它可以把指令转交给有写权限的 B，最终执行端仍要检查最初的授权来源。把授权视为请求链路的属性，不能只看最后一个发工具调用的组件。串谋关注多个参与者相互配合，合起来做单独观察时不易发现的违规行为。它和正常任务协作的可验收区别在结果及权限边界，例如各子任务单独都只返回少量合规数据，汇总端仍需要检查合并结果有没有超出整体可见范围。 Stanford 课件

在图上找读写边界

给实验室系统画一条最小链路。它包含身份验证、对话模型、预约查询、写入工具与数据库。再把公开设备说明和个人台账分开。公开说明可以检索，个人台账需要登录身份与范围校验。模型读到一个预约编号后，只能把它作为候选参数交给执行端。执行端还要确认资源归属、当前版本和本次意图。不要把后端凭据放进会话或工具结果里。

决策执行时检查什么有问题时记录什么
查空位设备可见范围、时间参数是否合法、返回字段白名单调用标识、被过滤的字段类别
查个人预约已认证用户和记录所有者是否匹配拒绝原因和审计标识，避免记录个人内容
取消预约资源归属、当前版本、获批的动作和有效期谁确认过什么、实际取消结果
执行重试同一身份与幂等键是否匹配原动作原执行编号和本次返回

校验分两类。一类检查形状，例如日期能解析、动作在注册表中。另一类检查权限与业务语义，例如用户确实拥有这条记录、当前操作的具体对象经过确认，写入不会导致非法状态。工具调用格式正确只说明应用可以解析请求。业务与授权决定是否执行。出现拒绝时也要返回可区分的状态，帮助模型解释或让用户重新确认。

沙箱补的是影响范围。若工具只需要查看一个工作目录，启动时就不要给它用户主目录或常用浏览器凭据。网络访问也可以限制在任务必须访问的服务，限制命令运行时间、输出大小与临时数据保留期。沙箱可以减轻工具程序错误的后果，但仍需表内权限。比如一个容器只能访问预约服务，它也可能使用该服务凭据发起不符合用户意图的取消。要覆盖这类错误，最终服务必须验证调用者与操作目标。 Stanford 课件

内容可以传给模型，授权仍由应用决定

一种设计是把模型用作动作选择器。应用预先定义可选动作，模型返回选中的动作和参数。执行器按表检查，未注册的动作无法执行。适合能力有限、流程较固定的助手。复杂系统可以在读取不可信内容之前先形成受约束的计划。后续结果只作为计划预先允许的数据输入，切换计划、扩大权限和增加敏感工具必须有重新审批的路径。设计时要留出「发现缺文件、需要人工帮助」的正常退出方式。

还有两类角色分开的思路。一个受限角色负责读外部数据，只产出结构化结果。另一个角色持有受控工具，并通过有限形式接收结果。仅把对话复制到不同模型实例，并不会自动建立隔离。如果高权限角色仍接收原始不可信内容，又可以自由决定新工具调用，原边界依旧存在。CaMeL 的论文将控制流与数据流分开，并在执行调用时用数据能力和策略限制私有信息的流向。理解机制时，可以关注结构化数据如何在不同权限的组件之间传递。具体安全结论需要结合论文的威胁模型和实现前提。 Agent 安全设计模式 · CaMeL 论文

输出护栏适合降低误发概率。例如文本中若含联系方式，发给公共渠道前可以要求结构化检查或人工复核。它不能代表真正的数据访问策略。如果字段从一开始就不需要，可以在检索阶段从返回值中移除。如果用户确实要共享，也要限制目的地与字段。PrivacyLens 研究关注模型在实际行动中是否遵守隐私规范。检验真实行为时要确认执行结果、数据内容及接收者。 PrivacyLens 论文

确认要绑定这次实际操作

「用户点过允许」需要落实为可检查的数据。取消操作可以绑定操作者、动作名、预约编号、预约版本与失效时间。交互中看到的确认界面来自这些结构化字段。用户确认后又调整了编号、日期或数量，旧确认不能继续用。后台也可能在确认和提交之间改变资源。执行时重新查版本，避免用户按旧状态作出的决定被用来改变新记录。对于真正的写入，要用事务或条件更新让校验与写入保持一致。

同一条命令的重试也分两种。一个请求可能还未执行就超时，也可能已经执行但返回丢失。应用不能只凭客户端看到超时来判断。用同一幂等键和请求指纹查询原执行结果，可以避免同一取消被处理多次。键应按身份隔离，复用时核对动作内容。若同一个键被拿来操作其他资源，应返回键冲突。日志里保存执行编号、结果和最少必要字段，方便用户查证。

用本地实验核对模拟台账的状态变化

下面的示例用 Python 标准语法模拟取消。身份、时间和批准记录由测试宿主提供，模型只提出预约编号。本节脚本在单进程内运行，用于展示状态检查，不替代生产鉴权与事务。

运行会得到 verified: only the approved booking changed。前半段验证拒绝后数据库不变，后半段验证获批的动作可完成、同一个请求返回同一个结果，并且其他预约未受影响。这里用 expires_at 表示半开有效期，所以 now == expires_at 时拒绝。如果改用数据库持久化，需要把幂等记录与资源状态一起提交，处理并发以及服务重启。服务端应为批准生成不可猜测的标识，批准来自可信界面，被测试代码在本地直接调用的方法不应暴露给模型。返回取消成功的字段也要来自已提交的结果。

把可用性和安全性一起测

设计测试前，写清目标对象与允许的行为。普通搜索应能返回允许展示的条目。修改对象超范围时，即使模型答复顺畅，外部状态仍应不变。对每条用例保存前后快照、尝试调用、返回值和拒绝原因。验收可以记录两组数字。合法任务中成功完成多少，越权或错误请求中有多少真正造成状态变化。两组数字分开后，才能看出防护是否建立了正确的边界。若两组请求统统被拒绝，即使越权变更为零，产品也失去正常能力。 Stanford 课件

模拟环境可以先用假账户、假记录和断开的网络做回归测试。线上监控则专门捕捉罕见的组合，例如重试激增、短期内连续读取大量记录、敏感动作突然换了目的地，或任务在止损参数附近反复循环。告警要关联请求标识和工具状态，便于暂停有副作用的流程。记录时避免把完整私密文档当作日志。用于复盘的访问权限与保留策略也属于设计的一部分。

把威胁模型变成可以验收的规则

只列「不要泄漏」会漏掉很多问题。可以借用课件提到的 STRIDE 分类给应用做一次检查，但每一类都要落到自己的数据和工具。例如身份冒用对应「预约服务只接收经验证的账号」。篡改对应「外部说明不能覆盖来源标注与预约版本」。抵赖对应「真正改过台账的动作有责任主体和执行记录」。信息泄漏、资源耗尽和权限提升，则分别要检查返回字段、执行预算和授权传播。分类用于提醒有哪些问题没问到，具体的准入规则仍按应用制定。 Stanford 课件

威胁本例怎样验收
冒用身份修改聊天文字里的姓名，实际调用仍只能使用服务端认证出的账号
台账被意外修改授权只读的任务跑完后，比对台账快照应无变化
动作无法追查每条变更都能从资源找到执行编号、发起者、批准版本和结果
信息被过度返回当前没有个人查询授权时，返回列表只包含设备、地点和可用时段
循环占用资源工具连续超时后能在预算耗尽前结束，不能一直排队重试
作用范围扩大另一个有写权限的子任务收到请求后，仍检查原始请求的资源约束

工具调用设置上限时，也要问终止后有没有遗留状态。比如后台写任务已经排队，模型先停止不等于外部任务撤销。可以在入队前给动作绑定到期时间，执行器收到过期消息时拒绝提交，并在日志中记录。需要取消时用队列自己的取消协议，或要求执行前检查一条可更新的状态。停止尝试、撤销已经安排的动作和补偿已完成的副作用是三种操作，应分别验收。课件对长任务错误累积和虚假成功报告的讨论，可以落实到这些具体状态。 Stanford 课件

用户可以同意「查我本人所有预约」，这不自动包含长期保留全部记录的权利。可读范围、可传输范围和存储范围分别定义。查看过保密备注还未必允许在对话里复述它。如果输出会发给不同接收者，就在确定接收者后再做字段检查。让模型在测试里回答「我会保护隐私」只检查它能说出规则。再给它实际的工具机会，看跨场景动作是否符合规范，才接近 PrivacyLens 关注的问题。 PrivacyLens 论文

上线后还要能收回权限。例如某个新增工具突然造成大量拒绝，先检查调用分布和失败标签，再考虑把新版本回退到只读模式。发布时把工具列表、策略版本与评测记录同行保存。回退后重跑最主要的正常路径和错误路径，确认原有任务还能完成，也避免把失败版本积累的待处理任务带进新配置。权限故障需要有给用户看的状态，例如「取消请求未执行，请重新确认」，同时给工程端保留没有敏感内容的执行编号。这样减少用户误以为任务已经完成，也便于排查是否有请求应该补偿。

把同一个应用的风险评审放在功能变更前后两次。第一次读结构，画出有哪些可信组件和外部输入。第二次拿可复做的用例看实际行为。一个功能如果从检索变成自动提交，即使系统底座没换，也应增加审批与状态变化的验收。字段如果从设备名称扩到个人联系方式，即使仍是只读，也要重新评审可见范围和保留期。能快速画出变化，通常比维护一份和应用脱节的通用检查表更有用。

实际验收时要同时测试「工具拒绝」和「决定不调用」。例如预约属于 B，本来就可以在页面上提示 A 无权修改。前置约束帮助手少走一步。执行端拒绝则保证即便模型仍发出请求，也没有变更。把两层分别记成策略结果和工具结果。这样改了模型的提示以后，即使模型开始发更多无效调用，你也能看出权限仍然有效、延迟和无效调用数却升高了。反过来，模型一直不调用也掩盖不了执行端缺少鉴权。测试应该包含在预期范围内直接检查宿主服务的场景。审批场景若有人工介入，检查确认界面和执行记录是否展示的是同一个资源与版本，避免用户以为确认了另一项动作。

练习 1｜给确认增加一个版本变化

让预约所有者始终是 A，但模拟批准后预约版本从 1 变成 2。预期老批准还在内存中，也应得到 approval_invalid，记录保留。接着重新确认版本 2，用新的请求编号提交，才会出现一次取消。检查失败前后的 bookings 和 completed，确认拒绝路径没有偷偷写入。上面的测试已经覆盖该流程。动手时可以删除版本字段，观察哪条断言能够发现回归。

练习 2｜设计一次只读的安全验收

设计一个库存答疑工具，公开结果只包含设备编号、空闲时间和地点。不论原始条目有多少附加字段，结果中都不应出现借用者的姓名、电话和内部备注。准备一条普通数据与一条含附加说明的数据，并准备一条已获个人查看授权的请求。预期公开两条都只返回允许的三个字段，个人授权也只用于本人记录。再让模型为三种结果写一句简短答复，评分器分别检查允许字段、模型说法与实际结果。这样能分辨泄漏发生在查询层、传给模型的上下文，还是最终答复。
