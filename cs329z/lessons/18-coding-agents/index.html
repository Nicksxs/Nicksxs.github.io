第 18 讲｜编程 Agent 从定位问题到验证补丁

根据 Stanford 课纲与原论文预习编程 Agent，拆解读仓库、编辑、测试、上下文与补丁验收。
  • CS329Z
  • LESSONS
  • 18-CODING-AGENTS

课程索引 · 下载 Markdown

2026 年 11 月 30 日 · 预习讲义。按发布时可见的课纲、论文和开发者文档整理。 Stanford 官方课表

开发者接到「导出 CSV 后最后一行丢失」的反馈，通常要问一句「哪个导出入口？」同样的问题交给编码 Agent，它也需要知道目标、仓库、允许操作的范围和验收条件。编程 Agent 能把搜索、编辑和执行穿成一个循环。工程工作的重点之一，是把循环中可能出错的地方暴露出来，让系统和开发者都能检查。

从 issue 到验收的完整循环

起点是 issue 描述和可读写的工作副本。Agent 读取目录结构、工具规则和相关文件，必要时做一个能失败的复现。它提交一小步编辑，再根据语法检查、测试结果或用户补充调整下一步。循环最终产出补丁、可以回查的测试证据和仍未验证的项目。执行端限制作业的时间、工具和资源。遇到反复失败、依赖无法安装或缺少授权时，系统可以返回明确的结束原因，保留已经完成的调查。 SWE-agent 论文 · OpenHands 论文

例如导出界面显示 3 条结果，下载文件里只有 2 条。先抓住可观察的事实。如果函数接到的列表已经只有 2 条，问题在选取数据或分页。如果函数看到 3 条、输出却只有 2 条，才优先看格式化和循环。把输入输出放在同一个短测试里，可以避免模型去改无关的表格界面。能复现以后，补一个最小修复，再跑更广的相关测试。若只读了一段源码就发现明显的边界错误，也应运行会暴露这个行为的测试，这样有前后证据。

循环阶段值得保存的观察常见误判
读仓库文件路径、调用入口、基准版本、相关测试找到同名函数就假定线上走这条路径
重现可控输入、预期与实际输出、退出状态用屏幕显示的条数替代实际输出
修改补丁差异与影响范围大幅重构后很难确定哪一处修好
验证目标测试和至少一组相关保留行为测试未收集到时仍宣称通过
结束修改摘要、有证据的结果、未验项把工具调用请求当成执行成功

有些修改要保持原有用户行为。比如修最后一行时，可能还需要保留字段顺序、引号转义和空输入输出。这些约束写进验证器以后，模型调整时才能看到具体的回退。代码审查也可以对照 issue 把额外变更拎出来，尤其是无关格式化、换依赖和扩大写入范围。

Agent 与计算机的接口是一项设计

SWE-agent 的论文把 Agent 面对终端、文件和编辑器的操作界面称为 Agent-Computer Interface。设计界面时，可以给模型清晰的搜索结果、带行号的局部文件窗口和结构化的编辑反馈。这些结果占用上下文，也影响下一步是否能找到相关分支。一个支持翻页的工具，需要让模型知道当前视图从第几行到第几行。一个编辑工具返回成功，也要说清改了哪段、是否有语法检查，方便下一步重读或回滚。 SWE-agent 论文

局部窗口的长度要由任务和代码结构决定。假设错误在循环末尾，完整判断却在函数顶部。模型只看到命中行上下 10 行时，可能误改局部判断。可以让它先用搜索找位置，再按符号、函数或相关调用者多读一段。反过来，返回整仓库会把大量代码塞给模型，增加成本，也可能遮住实际堆栈。课前做小对照时，固定任务、模型和最大工具轮数，只换「整文件」「命中摘要加窗口」的返回方式，观察命中是否包含正确文件、模型读了多少文本、最后是否过验收。 SWE-agent 论文

不同系统对操作接口取舍不同。OpenHands 论文讨论了如何把模型接到执行环境，提供文件、终端等软件开发操作，以及如何用平台运行不同类型的任务。Claude Code 的公开工程文档则从实际项目协作出发，讲运行前准备、项目指令、验证反馈与上下文的用法。可以拿同一个 issue 对照这三种资料，分别画出模型请求、工具操作和环境反馈如何连起来。产品迭代较快时，参考对应论文或文档版本，避免把某个版本的默认工具设定当成所有部署的行为。 OpenHands 论文 · Claude Code 工程文档 · Stanford 官方课表

当前状态和长任务怎样保下来

一次调试需要的信息很具体。包括基准版本、当前假设、修改过的文件、目标测试的最后一次状态，以及下一步要看哪里。把整段对话当作唯一持久状态会遇到两个问题。上下文可能需要压缩，前几次关键信息不一定能重放。工作环境可能另有改动，旧消息说「文件没变」也可能过期。适合持久化可核验的状态，如任务清单、提交或差异标识、测试命令与退出状态。下一轮可以先读这些记录，再重新确认关键文件。 Agent 设计模式课件

观察接口要让 Agent 知道发生了什么

编码工具的失败至少分三类。调用参数不合约，例如路径为空或范围颠倒。调用合法但环境出错，例如文件已移动、读取超时或依赖缺失。还有调用成功却没有达到目标，例如替换工具没有找到匹配项。对模型来说，这三种反馈都可能变成一段文字。如果接口把它们统统写成「完成」，下一轮就会继续建立在错误状态上。接口可以把 exit_code、matched_count、changed_files 和 next_hint 分开，返回实际可用的诊断。 SWE-agent 论文

替换操作尤其需要检查前提。在 CSV 示例里，目标字符串 rows[:-1] 可能在两个文件各出现一次，也可能因为别的改动已经消失。工具如果默默改所有命中位置，就扩大了补丁范围。更可靠的编辑参数会指定路径、原片段与期望匹配次数，必要时附上读取时的文件版本。匹配结果为零或多于预期时，先重新读取，确认是哪一处。成功后比较差异，再用解析器或测试检查语义。行号可帮助定位，却不能单独代表版本。其他人插入一行后，旧行号可能指到了别处。

终端工具也应指明工作目录。如果同名测试文件存在于两个目录，模型可能在错误的副本执行命令。执行回执应把命令、工作目录、退出状态和日志标识一起保存。输出太长时，可以保留开头的命令上下文、最后的总结和可请求的详细段落。仅截取结尾有时会丢掉第一个真正错误，而它通常是后续连锁报错的根因。仅截取开头则可能遗漏收集到多少测试、有没有运行到报告阶段。观察截断策略应与测试框架和预算一起试。 SWE-agent 论文 · Stanford 框架课件

还要考虑工具状态与模型状态的同步。一个编辑请求发生超时，可能是并未执行，也可能是执行完成后响应丢了。盲目重发替换很容易造成重复编辑。先重新读取目标，核对原片段和修改后片段，再决定是否重试。对于生成文件的动作，输出文件名可以和动作编号绑定，方便查询有没有完成。测试命令通常可重新执行，但必须明确它是否修改缓存、数据库或外部服务，重跑之前用同一隔离策略重置环境。

把上下文当成可以调试的输入

编码 Agent 常需要读规则、项目文档、调用者源码、历史差异和测试输出。每轮模型请求可以只包含眼前任务需要的信息。一个简单策略是按任务逐步读取。开始给项目规则和目录概况。找到范围后给目标函数、相关调用者和一条失败轨迹。修改后给差异、目标测试与保留测试结果。留下来源路径和版本号，有歧义时工具可以重读。这样即使必须压缩旧消息，也不会只剩下一句「先前已处理」。 Agent 设计模式课件 · 长任务运行底座说明

用下面的方式定位上下文问题。Agent 总改错文件，先看搜索结果有没有正确路径，随后检查输入里是否注明真正的调用入口。它找到正确文件却反复修错，读工具反馈是否缺少异常分支或函数完整边界。它已经改对但没有验证，查看测试命令是否在工具权限里，以及预算是否用完。它跑完测试却总结错误，可以检查工具回执是否把失败计数与退出码分开。各故障对应的调整不同，分别改动一次才能在评测里确定收益。

如果有自动压缩摘要，保留任务编号、已变更的文件、最后看到的补丁、尚未验证的约束和日志索引。清空上下文再恢复时，要求系统重读实际文件，核对是否发生外部变更。可以专门测试两种恢复场景。第一种修改完整但没开始验证，预期恢复后开始跑验收。第二种同一文件在中断期间被用户改动，预期系统先查看差异，保留用户改动并重新定位。把所有状态只放在聊天文本里很难应对这两种情况。

怎样比较不同的运行底座

比较框架时，至少固定任务、基础模型和环境。比如在 6 道本地数据导出题中只比较「整文件读」和「按函数定位读」。两组实验用同一个验证器和相同的最大工具轮数，记录退出原因、路径命中数量、累计返回文本字符数、目标测试通过和保留测试回退。若同时更换模型，就把结果写成两个完整系统的比较。因果结论应限定在能够控制的变量上。 Stanford 评测课件

也可以把分数拆成工作流程指标。找到目标文件的比例反映定位。成功应用的修改比例反映操作。通过所有目标和保留测试的比例才反映任务达成。假设模型 A 经常找对路径却改不到文件，优化工具语义或工作目录可能比加强搜索更有效。模型 B 多数补丁能应用，但破坏空输入、编码或时间边界，就该增加相应诊断和用例。当系统升级以后，保留失败路径的轨迹可以告诉你，提升是否来自更准确的定位，还是恰好删掉了一条困难测试。

把成本一起报告时，说明计的是模型调用次数、输入输出 Token、工具时间还是端到端时间。例如并行测试使总工具工作量更大，却缩短用户等待。精准定位使读取字符数减少，却可能增加翻页次数。两个结果都可能合理，应该和任务成功率并列看。也要记录无法评分的情况。环境没启动时没有候选补丁，不能记作某个目标测试失败。反过来，如果用户关心的是整个工具能否顺利工作，也应报告包含环境错误的总体完成率。 Stanford 评测课件

练习一｜用真实解析结果验收 CSV 补丁

这里构造三种手写实现。第一版错误地跳过最后一条，第二版保住行数，却把 CSV 当作普通逗号拼接，第三版用标准库正确写出。验收用标准 CSV 解析器读取输出，分别比对数据数量、内容和空输入约束。这个脚本不调用模型，用来演示怎样评价 Agent 可能提出的两类修复。

运行结果中的 single 对应原 issue 的最小输入。empty 检查旧客户端期待的表头。comma_field 检查「保留行数」有没有掩盖字段结构的回退。第二版虽然通过了最直接的两项，仍不满足编码契约。最后一条专门放了字段内的单独回车字符。标准方言的行终止符是 CRLF，写入器会给包含单独回车的字段加引号，读回时仍是一条记录。编写测试时要先确定原因和标准，别把候选实现的具体写法变成评分要求。例如可以用手动正确转义的方法解决，验收应承认其输出，只要它满足同样的契约。

可以追加两类样本。用 他说"归还" 检查引号转义。再用字段内真实的换行，检查消费者能否解析成一条记录。把两种输入各做为只含一条数据的独立用例，同步更新预期字典。对带双引号但没有逗号的字段，直接拼接有时会碰巧解析正确，例如引号位于字段中间。测试可以选择以引号开头的字段，覆盖解析器会将首字符识别为引号的情况。这时按物理行数评分会给出错误结论。对多平台项目，可以在真实支持的环境上再跑一次，记录读写文本的编码与换行策略，避免拿一个平台的通过结果替代其他环境的结果。

练习二｜区分能否使用工具和能否解决问题

把两个 Agent 配置保留在同一个干净试验仓库里。配置 A 能读文件和执行测试。配置 B 只能读文件，但同样可以提出补丁文本。给它们相同的说明，固定模型和预算，独立启动。要求两个候选都产出补丁，最后由同一个外部环境应用并运行验收，比较结果。这样可以分别记录「候选自己实际运行了哪些测试」和「外部验证是否通过」。B 没有执行权限，应如实报告它没有运行测试。外部验收仍可能证明它产出的补丁正确。A 执行了测试，也可能因为只跑了不相关的用例而提交错误补丁。工具使用和任务达成是两条证据。

准备一个空实验记录并填写预期观测。两边环境起点相同、评分器版本相同，所有差异都在接口和轨迹。记录文件读取范围、是否定位到导出函数、是否运行过目标用例、补丁是否通过。假如 B 的生成结果没办法应用，先记成补丁格式问题。假如 A 通过目标却破坏逗号字段，记成回归失败。用这些标签复盘，比单问「哪个 Agent 更强」有用。 官方评测课件

代码能跑之前，先写清执行权限

让 Agent 看公开仓库，和让它改用户的默认分支，是两种权限。工作副本可以先限制目标目录与可写路径，把真正发布、删除、外部通信和使用凭据留给明确确认。测试应在隔离环境内运行，必要依赖从可信来源获取。看到 issue 推荐运行一段命令时，先用应用的信任和权限规则判断是否执行。工程上可以给部署与写入工具单独的能力，让日常读和改无需掌握发布凭据。这样即使模型判断失误，外部影响也由工具契约约束。 Agent 安全课件
