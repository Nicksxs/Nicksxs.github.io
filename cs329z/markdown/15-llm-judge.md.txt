还是拿设备借用来说。系统有没有写入预约，用代码查表就够了。它有没有讲清楚冲突原因和下一步选项，则可能存在多种合理表达。把这两件事混成一个「整体满意度」分数，看到分数下降时就很难定位哪里坏了。

## 先给裁判可以核查的依据

官方课件讨论了代码评分、模型评分和人工评分。对预约时间、记录数量这些有明确答案的检查，可直接用代码。对「冲突解释是否与证据相符」，可以给模型裁判用户请求、库存查询结果和判定标准。让它分别判断回答是否说清冲突、是否提供适用的下一步、是否编造已完成的预约。抽取一批样本让人复核，记录裁判把错误答复判为通过的比例，也检查漏掉多少合理答复。 [第 15 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture15.pdf)

单独评分容易把每条答复的判定记录下来，成对比较适合问哪条解释得更清楚。成对比较时，把两条回复换个顺序再评，看结论是否改变。检查长度偏好时，用意思和事实一致的长短两版。混入金额或时段错误后，评分差异就同时受到长度和事实正确性的影响。 [MT-Bench 与 Chatbot Arena 论文](https://arxiv.org/abs/2306.05685)

## 一次成功和次次成功怎么数

同一题跑 4 次，观察到两次成功。任取两次，共有 6 种组合。至少一次成功的组合有 5 种，`pass@2` 的组合估计是 `5/6`。两次都成功只有 1 种，`pass^2` 的估计是 `1/6`。前者适合分析能尝试多次且有验证器选出正确结果的系统，后者强调重复尝试时的稳定性。评测多道题时，先按题计算再平均，同时报告每题重跑次数和预算。运行设施应给每次尝试重置初始环境，保存轨迹、最终状态以及评分器版本，方便之后基于同一批记录重评。 [第 15 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture15.pdf) · [τ-bench 论文](https://arxiv.org/abs/2406.12045)

## 先决定什么算失败，再决定让谁来评分

给借用助手一条任务「帮我借周五 9 点到 11 点的无线麦克风」。库存显示 M01 有重叠预约，M02 是有线设备，用户没有接受替代品。最终数据库仍旧没新增记录。假设系统说「M01 在 10 点到 10 点半已借出，我可以为你查同类设备，或者问你是否接受有线」。数据库层可以确定系统没有误写，可以核对 M01 确实冲突。至于这句答复有没有准确解释问题，以及提供的选项是否合理，需要结合原请求和用户的选择边界判断。

可把这项评测拆成三组。代码评分读取最终表、操作轨迹和数据格式，关注设备、时段和是否授权。模型评分对照用户请求和工具证据，看答复有没有把冲突说对，以及是否承认还在等待用户决定。人工复核检查模型是否漏掉特殊情况，例如设备名里写了无线，实际版本标记带线，模型把其中一个字段误当作唯一依据。人和模型也可以分别判同一批样本，目的在于核查自动评分是否已经适用于这个任务。

| 评分对象 | 可以使用的证据 | 如何判 |
| --- | --- | --- |
| 有无写入记录 | 初始表和最终表、写入返回 | 检查主键、借用人、设备和时段 |
| 写入是否发生在用户确认之后 | 可信工具与确认事件的顺序 | 发现无授权写操作就单独记录 |
| 冲突解释是否准确 | 原请求、库存冲突的起止时间 | 引用事实可追溯到输入证据，不能把候选说成已预约 |
| 下一步是否可行 | 已知免借用条件、用户允许的范围 | 可询问缺失信息，也可以提出在限定范围内的下一步 |
| 表述是否容易理解 | 最终答复，以及读者需要完成的事项 | 在事实核对后再评清晰度，难例可请人复核 |

先把确实不能接受的错误单列。比如未经确认就写入，即使答复优美也不能补偿。语言和帮助性若足够有交集，可以通过多个维度给分，但每个维度的目标都要写出来。给模型裁判「这条回复几分」很容易让它自己决定评分标准。给它「三项检查，各自引用依据」，则更容易判断哪项结果可以用，哪项仍需修改。课件讨论了全部检查必须通过、按权重汇总和人工校准等组合方式。 [第 15 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture15.pdf)

### 一份可以人工复核的评分表

下面是一种演示输入。工具事件已按来源标识。用户请求、工具报告和待评文本分开提供。模型如果认为某条依据缺失，可以返回「无法判定」。把证据标识一起收回来，可以复查它引用的是独立的工具事实，还是候选答复对自己的描述。

```text
任务：解释当前无法借到 M01 的原因，给出一个可行下一步。
E1 用户要求：周五 09:00–11:00，无线设备。
E2 库存查询：M01 在 10:00–10:30 被占用，M02 为有线型号。
E3 环境快照：没有新预约。没有改借其他型号的确认记录。

待评答复：
「M01 在 10:00–10:30 已有人借用。我可以帮你查找另一支
无线麦克风，你也可以确认是否愿意改借有线型号。」

检查项
- conflict_explained：是否把 M01 的冲突说清楚，时段是否与证据一致？
- status_supported：是否避免声称已经预约？
- next_step_allowed：下一步是否在当前权限与条件内？

每项返回 pass、fail 或 insufficient_evidence，附证据 ID。
```

这条答复三项都应通过。再写一个差异很小的反例。「M01 在 10:00 到 10:30 有冲突，我已经为你改借 M02」。第一项可以通过，后两项都应失败，因为它声称已有预约，而且用户尚未同意。两条答复看起来都很礼貌，只有用事实和权限标准并排核对，才能看出区别。实际工作里可以要求裁判在选择「无法判定」时指出缺少的库存字段或操作证据。模型裁判给出的解释是复核线索，证据是否支持解释仍要独立检查。

记录评分结果时把任务、尝试、评分器和证据版本都带上。这样可以对同一次运行重判，也可以比较两个评分器对哪些样本意见不同。下面是一条预期评级的 JSON 示例。它是可以用于调试表格的合成记录，没有经过模型打分。

```json
{
  "task_id": "campus-audio-conflict",
  "trial_id": "fixture-01",
  "grader_version": "booking-rubric-v1",
  "evidence_version": "inventory-fixture-a",
  "state_checks": {
    "unexpected_mutation": false,
    "expected_to_wait_for_confirmation": true,
    "write_events_seen": 0
  },
  "answer_checks": [
    {"id": "conflict_explained", "result": "pass", "evidence": ["E1", "E2"]},
    {"id": "status_supported", "result": "pass", "evidence": ["E3"]},
    {"id": "next_step_allowed", "result": "pass", "evidence": ["E2", "E3"]}
  ],
  "final_status": "pass",
  "label_source": "expected_behavior_fixture"
}
```

如果某个维度全部缺证据，汇总表应显示缺失率。一些系统把无法判断当成通过，会掩盖证据采集失败。另一些系统把它全当成普通失败，又会把评分器问题混进被测系统的结果。较易诊断的做法是保留未判定标签，明确发布通过率的分母，并在专项调查中先看看缺哪些字段、这些字段本来应从哪里取。

## 从读文本到检查真实产物

课件从几个研究阶段介绍模型评分。早期的做法希望超越文本重合率，提高摘要或对话这类开放文本的评价质量。G-Eval 给模型明确定义的评价维度，并使用模型给各档分数的概率汇成分数。它关注的是给定任务下模型能否和人工评价接近。不要把相似分数当成事实等价，也别默认一个总结评分器对不同领域或文本风格都能等量工作。更换应用场景时，可以从关注点固定的小数据集重新校准。 [G-Eval 论文](https://aclanthology.org/2023.emnlp-main.153/) · [第 15 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture15.pdf)

偏好评测把问题换成「两个输出里哪个更好」。它适合比较同一任务的多种合理答复，例如哪条交代得更清楚。相对偏好可以汇总成胜率，但它回答的是工作条件下的相对选择，无法直接告诉你系统是否满足最低要求。一对回复可以同时出错，裁判仍可能被迫选一个。设定允许平局、都失败或证据不足，能让错误被看见。绝对评分可以直接用统一量表做门槛，前提是量表足够具体，并且换批次后不会自己漂移。 [MT-Bench 与 Chatbot Arena 论文](https://arxiv.org/abs/2306.05685)

Agent 评测进一步需要核查环境。普通文本裁判只拿到最后一句「完成了」，无法知道数据库是不是被改过。给它一份可信的环境快照与动作日志，它才有材料核对。如果任务产物涉及许多文件，也可以给评分系统有限的只读查询能力，由它从工作区取证。Agent-as-a-Judge 研究把这种核查做成可检查工作区的运行流程。这样的评分器自己也需要试验校准，还有额外成本、查错文件和遗漏证据的风险。以设备借用为例，只有一张预约表时，代码查表比再派一个智能体更直接。 [Agent-as-a-Judge 论文](https://arxiv.org/abs/2410.10934)

检查环境的评分器要和被测轨迹隔开。待评文本可以包含不准确的承诺。文件里的注释也可能试图改变评判方式。评分器应把这些内容当成待评材料，不从里面更新评分规则。若可以读工作区，让它只读本题可查的路径，写入和外部发布权限留在环境边界之外。和模型裁判并用的状态检查应该直接读取可靠的结果记录，避免两套评分都只听助手说了什么。

## 交换位置只是第一步，校准还要看具体错法

把短回复 A、长回复 B 放进去做成对判断。在第一次中 A 是选项 1，第二次把 B 放到选项 1。要先把两轮的选择都映射回 A 或 B，再判断结果是否一致。两个文本保持不变，仅交换顺序。如果裁判两次都选「第一个」，说明两次偏好结果实际上相反。真实数据中偶尔不一致还可能由生成波动引起。用一组任务多次判断，才能区分稳定的位置效应和偶尔翻转。

测长度影响则要让两条回复保留同一套事实和许可边界。拟写两版，短文两句讲明冲突与选择，长文把相同事实分成更细的句子，但不加新信息。它们长度变化，任务满足程度保持一致。若加入了一条错时段，又同时把文本变长，就不能只把分数差归因给长度。课件也提到 Length-Controlled AlpacaEval 用统计方法估计长度相同时的偏好。在业务小样本里，可以先用控制过的成对文本诊断。 [第 15 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture15.pdf) · [Length-Controlled AlpacaEval 论文](https://arxiv.org/abs/2404.04475)

自我偏好也值得单独查。给裁判隐去文本来源，放进相同规则、不同系统产生的回复。保留一份人给的判断，不仅计算整体一致率，还看它是否对特定来源、文风或题型系统性放宽。在标签本来就不太一致的场景，先修正任务的判断标准。可以让两人独立标注，再集中讨论分歧，把无法定案的样本留作难例。用一组材料调量表和例子，再用另一组看修改有没有迁移。直接拿校准组算最终一致率，常会高估实际效果。

AutoMetrics 展示的是另一条校准路径。在已有指标和生成的模型评分标准中选择候选，用人标的数据组合它们，再看模型评分与人类判断能否接近。对校园借用这种小系统，可以先把「有无误写」「冲突解释准确」「下一步可行」存成独立列，在一批人工标注上看哪列误差最大。若大部分误判都出在下一步权限，就先补权限证据和说明，不立即增加更多模型投票。同一个有偏裁判多跑几次可以帮助分析波动，但稳定的偏向不会因此自动消失。 [AutoMetrics 论文](https://arxiv.org/abs/2512.17267) · [第 15 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture15.pdf)

### 用假数据算一遍误判

假设一份保留集有 20 条回复，人工判 12 条通过、8 条失败。裁判把 10 条合格回答判过，判错了另外 2 条。又把 3 条不合格回答放过，认出了剩下的 5 条。整体一致是 `(10 + 5) / 20 = 75%`。对「能不能作为改动发布门槛」这个问题，还要看 8 条人工失败中有 3 条被放过，对应 `3/8`。如果这些都是未授权写入，先加入代码检查。若多是语义误判，则要看裁判是否缺少工具证据。这个数字是手算示意，不代表任何模型的准确率。

| 人工判定 | 裁判判通过 | 裁判判失败 |
| --- | ---: | ---: |
| 通过 | 10 | 2 |
| 失败 | 3 | 5 |

把这四个格子留在报告里，一致率变化时就能看到是哪一种错少了。样本更多时，按场景拆开汇报。系统在正常预约上比较一致，不意味着它对跨校区政策也同样准确。要统计变化，换裁判或提示时对同批冻结记录重新打分，再独立重跑若干任务，以便区分评分方法变化和 Agent 行为变化。

## 把多次重跑的分数算到任务层面

上面的四次试跑只是一个任务。用公式写，假设某题实际跑了 `n` 次，其中 `c` 次成功，关心从这些试跑里取 `k` 次。组合数 `C(n,k)` 表示不区分顺序地选出 `k` 次的办法。全失败的组合是 `C(n-c,k)`，全成功的是 `C(c,k)`。从 1 减去全失败的比例，得到至少成功一次的估计。全成功的比例则直接估计每次都成功。规定 `1 ≤ k ≤ n`，不足 `k` 项的组合数记作 0。把同题不同尝试视作可比较的试验，需要把每轮的环境和约束重置到同一条件。

设任务 X 的 4 次尝试通过 2 次，任务 Y 的 4 次尝试全部通过。两题单次平均是 `3/4`。逐题算 `pass@2` 得 `5/6` 和 `1`，平均是 `11/12`。逐题算 `pass^2` 是 `1/6` 和 `1`，平均是 `7/12`。另找两个都只过了 3 次的任务，单次平均仍为 `3/4`，两次全成功的估计却都是 `3/6`，平均变成 `1/2`。总体单次平均相同，相同任务的波动情况不同，多次成功的指标也会变。 [第 15 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture15.pdf) · [τ-bench 论文](https://arxiv.org/abs/2406.12045)

重复运行时另存每轮的成本、异常情况和停止原因。若工具上一轮写入没清理，这一轮命中缓存或已存在的数据，指标就不再回答同一问题。对用于搜索和代码候选的系统，允许尝试多次再由独立检查选出成功是合理设计。面向用户每次都要写预约的系统，则要看每一轮都可靠完成的能力。不能为了求更好的分数，在有副作用的生产系统里盲目重复提交。

### 给裁判升级留回退路径

裁判提示、模型和评分量表有各自的版本。只改其中一个时，可以先取一批已有人审的失败样本，在旧裁判和新裁判上重评。让人工集中读判定发生变化的那部分，检查是新裁判能解释证据，还是它忽然降低了通过要求。若准备从每项必过调整成加权评分，同样要用已知的硬错误验一次，确认其它项目加分后仍无法覆盖越权行为。

运行预算也可以按证据难度分配。常规写入由代码核对，只有存在多种解释或出错原因说不清时才使用模型评分，裁判意见分歧或证据不足时再请人看。每轮同时记录各层实际处理的题数和成本。换成更多次模型打分后，即便结果更接近人工，也要看它减少的是漏判哪类重要错误。若只让无关的风格判定更一致，用于事实检验的收益就有限。 [Anthropic 的 Agent 评测实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 练习 1｜做一个有可判定结果的裁判对照

准备固定冲突记录和四份答复。A 短且准确，B 长且准确，两条提供相同事实。C 和 B 长度接近，却声称 M02 已预约。D 不确定是否完成，明确请用户核查或继续确认。先由人使用本文的评分表逐项核对。再对 A/B 和 B/C 各做两次成对判断，每次交换顺序。采用模型时可限制结果为 A、B、平局或证据不足，并另外保存单条回复的三项判断。

**预期核对**。A 与 B 的事实维度都应通过。B 与 C 在事实正确性上应有稳定差异。D 不应被当作说了「已经完成」，仍需核对它建议的下一步是否合适。若 B/C 换序就改变选择，先查位置偏好。若 A/B 总偏好长文，但事实判定相同，可以把偏好和事实得分分开记录。只做纸笔检查时，结果验证的是评分设计。实际调用后，报告使用的模型、提示版本、顺序与逐项记录。

## 练习 2｜核对两种多次成功指标

下面用 Python 标准库核对两个虚构数据集。把组合比例保留为有理数，方便手算对照。每个任务内的列表只记录通过与否。实际运行还应保存对应的环境版本、执行异常与费用。

```python
from fractions import Fraction
from math import comb


def summarize_trials(trials, k):
    n = len(trials)
    if not 1 <= k <= n:
        raise ValueError("expected 1 <= k <= number of trials")
    if any(type(result) is not bool for result in trials):
        raise ValueError("every trial must have a Boolean verdict")
    c = sum(trials)
    denominator = comb(n, k)
    pass_at_k = 1 - Fraction(comb(n - c, k), denominator)
    pass_hat_k = Fraction(comb(c, k), denominator)
    return Fraction(c, n), pass_at_k, pass_hat_k


def macro_average(tasks, k):
    if not tasks:
        raise ValueError("provide at least one task")
    per_task = [summarize_trials(row, k) for row in tasks]
    return tuple(sum(column) / len(tasks) for column in zip(*per_task))


suite_a = [
    [True, True, False, False],
    [True, True, True, True],
]
suite_b = [
    [True, True, True, False],
    [True, True, False, True],
]
expected_a = Fraction(3, 4), Fraction(11, 12), Fraction(7, 12)
expected_b = Fraction(3, 4), Fraction(1), Fraction(1, 2)
assert macro_average(suite_a, 2) == expected_a
assert macro_average(suite_b, 2) == expected_b
for name, dataset in [("A", suite_a), ("B", suite_b)]:
    print(name, *(str(value) for value in macro_average(dataset, 2)))
```

运行后输出 `A 3/4 11/12 7/12` 和 `B 3/4 1 1/2`。把 `k` 改成 1，可以看到两个指标在同一题上都退回到单次通过比例。再加一题只有两轮试跑，选择 `k=3` 时程序应报错。若遇到评测基础设施异常，应先约定这个结果如何纳入或额外汇报并保留异常标记，别悄悄把未执行样本丢掉再改变分母。
