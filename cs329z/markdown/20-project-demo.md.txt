# 期末项目｜把 Agent 演示做成可复现的评测

[课程索引](/cs329z/review/) · <a href="/cs329z/markdown/20-project-demo.md.txt" download="20-project-demo.md">下载 Markdown</a>

2026 年 12 月 9 日 · 项目演示准备，依据 Stanford 官方项目要求和评测课件整理。 [项目说明](https://cs329z.stanford.edu/project.html)

演示里，设备预约 Agent 一次查对了空位。听众很快会问，如果用户不给时间，如果同一台仪器在同一时间已经被占用，如果数据库超时，它还会怎样？把这些问题放进任务集后，演示才有了可以核验的基础。本篇从一个很窄的校园场景出发，整理到提案、对照实验和交稿。

## 提案要把问题、用户和验收写在一起

「用 Agent 帮实验室管理设备」范围太大。它可能包含查政策、看空位、提交预约、追催归还甚至维护台账。可以收窄成「接受自然语言的查询，判断指定设备在给定时段是否可借」。首版只读，不做实际预约。目标用户是需要借公共设备的同学。成功条件包括正确识别设备、检查时段、查询当前台账，并给出与查询一致的状态。如果输入缺了结束时间，系统应该追问。写明这条行为后，评测才能区分合理的澄清与漏答。

Stanford 项目说明要求早定义评测任务、说明数据如何得到、定义怎样算成功，并进行有意义的基线或对照。期末不能靠单次演示代替评测。选题若过于开放，先从一组可以稳定验收的任务开始，再增加多步交互。也可以选择专注于严谨地评测现有 Agent，而不是从零搭一个新服务。 [官方项目说明](https://cs329z.stanford.edu/project.html)

写提案时可以先填四行。

| 要写的内容 | 设备预约例子 |
| --- | --- |
| 用户与任务 | 同学问示波器在指定时段是否可借 |
| 最小可行方案 | 解析设备名和时段，查一份只读台账 |
| 基线 | 根据表单中的设备编号和起止时间，用规则检查 |
| 要验证的改动 | 把设备俗称映射到编号，比较有无冲突校验的差别 |

这张表有一个好处。团队可以沿着它拒绝暂时无关的工作。如果还没有正确的台账查询，接入记忆系统也证明不了用户的核心任务已解决。先建立可验证的基础，然后再加模型解析、检索、工具循环或更丰富的交互。

## 把一组题写到别人可以重跑

给每道题一个稳定编号，保留输入和起始数据。业务规则按有明确语义的方式写出。例如同一设备的重叠判断使用半开区间，起点包含、结束不包含。这样一台设备已经借到 11 点，11 点开始的预约仍允许。样本里同时放普通、边界、异常三类场景，再给它们加独立标签。发生回归时可以知道是哪类先下滑。

任务定义写清请求、环境和验证方式。评测协议另外规定预算、尝试次数、失败处理和报告口径。输出依据来自应用的外部状态或稳定记录。只读工具至少要保存查询参数、状态与来源标识。涉及写入时要验收新的状态、数量和权限。工具错误和正常空集要分开，表格打不开时返回「没有预约」会把故障伪装成正常结果。 [官方评测课件](https://web.stanford.edu/class/cs329z/slides/lecture13.pdf)

训练、调参或完善提示使用一套开发样本。最终验收用另一套未参与选择的样本。如果几个近似问题都来自同一设备和同一时段，可以按场景分组切分，避免答案相似却落在两边。期末数据不够大时，不要假装有统计精度。保留原始计数、具体失败和暂未覆盖的场景，比堆一个小数点更有信息。

## 用四组配置区分两项改动的效果

一个有效对照尽量只改变一处。如果系统从「不认俗称也不查冲突」跳到「认俗称并查冲突」，只能说组合行为有变。想知道各自贡献，就保留两种中间版本。下面用确定性代码演示四种设置，输入是人工结构化的虚构数据。所有配置共用评分器，无模型、网络和真实预约。这个实验说明怎样设计消融，不能用于评价某个模型。

```python
DEVICES = {"S1", "C1"}
ALIASES = {"示波器": "S1", "相机": "C1"}
BOOKINGS = {"S1": [(10, 11)], "C1": [(12, 13)]}

CASES = (
    ("exact_free", "S1", 14, 15, "available"),
    ("exact_busy", "S1", 10, 11, "conflict"),
    ("touching", "S1", 11, 12, "available"),
    ("alias_free", "示波器", 14, 15, "available"),
    ("alias_busy", "相机", 12, 13, "conflict"),
    ("unknown", "镜头", 10, 11, "unknown_device"),
    ("missing", "S1", 10, None, "need_info"),
    ("bad_interval", "S1", 11, 10, "invalid_interval"),
)


def predict(device, start, end, *, map_alias, check_conflict):
    if start is None or end is None:
        return "need_info"
    if not 0 <= start < end <= 24:
        return "invalid_interval"
    if map_alias:
        device = ALIASES.get(device, device)
    if device not in DEVICES:
        return "unknown_device"
    if check_conflict:
        overlaps = any(start < taken_until and taken_from < end
                       for taken_from, taken_until in BOOKINGS.get(device, ()))
        if overlaps:
            return "conflict"
    return "available"


variants = (
    ("baseline", False, False),
    ("aliases_only", True, False),
    ("conflicts_only", False, True),
    ("combined", True, True),
)
expected_counts = {
    "baseline": 5,
    "aliases_only": 6,
    "conflicts_only": 6,
    "combined": 8,
}
for name, aliases, conflicts in variants:
    failures = [
        case for case, device, start, end, expected in CASES
        if predict(device, start, end, map_alias=aliases,
                   check_conflict=conflicts) != expected
    ]
    passed = len(CASES) - len(failures)
    assert passed == expected_counts[name]
    print(name, f"{passed}/{len(CASES)}", ",".join(failures) or "-")
```

输出如下：

```text
baseline 5/8 exact_busy,alias_free,alias_busy
aliases_only 6/8 exact_busy,alias_busy
conflicts_only 6/8 alias_free,alias_busy
combined 8/8 -
```

同样是 6/8，两种中间版本漏的题并不相同。只查冲突解决有准确编号的占用问题，能识别俗称则解决有空位但设备名称不同的问题。`alias_busy` 需要两项一起工作，不能把新增 3 道通过简单平分到两个模块。报告里要列出改变的样本和原因，避免把这个小数据集上的结果推广到所有场景。

也可以做一份清晰的升级路线。先用程序验证时段与占用。再拿一组固定用户表达测试模型提取日期、时间和设备名，把字段传给同一套规则。随后再接用户澄清和工具异常处理。每次只增加一个环节，保留之前的题。如果引入多步 Agent，要记录每步的操作与停止原因，把最终状态和自然语言质量分别评分。

## 报告和演示各需要什么证据

提案阶段说明问题、关联课程内容、基本方案和验收思路。中期应已有可运行原型，报告说明环境、数据、方法与进展，并附能运行原型的代码仓库和 README。最终演示用一条成功轨迹与一条失败轨迹解释工作流程，再用任务集对照给出结果与局限。正式报告的格式、提交时间、作者贡献说明与 AI 使用披露应按官方要求核对。 [官方项目说明](https://cs329z.stanford.edu/project.html) · [课表与截止时间](https://cs329z.stanford.edu/)

一份结果表可以同时有完成率、耗时和外部操作次数。每项指标说明分母。耗时从收到请求计到什么状态？模型和工具各占多少？失败运行要不要进入统计？如果测试平台的依赖装不上，应记录为环境错误，再报告哪些任务实际进入评分。报告可以同时给全样本与可评分样本的计数，但要说清用了哪个决定主要结论。对并行工具或重复尝试，额外标记实际资源消耗，避免把其中一次最好结果当作日常表现。

失败分析的重点在因果证据。「模型推理能力差」太宽。比如查询在解析俗称前就直接返回，可以跟着轨迹定位到路由顺序。写入时查到旧状态，则需要看数据快照和记录版本。测试判错要复查验证器是否执行及命名是否匹配。记录第一个可以证实的偏离点，再看后续有没有恢复。若无法定因，留下复现步骤和缺的证据。

## 让另一台机器从空目录复现

README 包含依赖版本、支持的运行环境、如何提供模型凭据、怎样构造样例数据和启动系统。说明如何运行评测、生成产物和对比分数。不把真实凭据放入项目。具备外部依赖的系统可以另给一条离线冒烟路径，让别人先确认工具循环、评分器和状态日志工作，再进入实际模型试验。离线替身与真实模型的输出分别保存。

演示前可以做一次独立复现。另一个人按说明，从空目录拉取固定仓库版本，跑一条普通、一条边界、一条失败样例，找到对应的输出与评测日志。最后再跑整组任务，看版本、结果文件和失败标签是否对得上。会变的外部 API、模型版本或远端数据明确标在运行配置中。找不到某次评分或只能从演示视频里猜测数据，就把这项标为待补。 [官方项目说明](https://cs329z.stanford.edu/project.html)

## 按阶段交出能继续工作的东西

课堂项目说明把提案、中期展示和最终报告分成几个阶段。提案写清楚问题、相关工作、可行方案与验证计划。中期重点在已有可运行原型、数据与环境的准备、方法和实际进展。最终报告则把这些证据放进完整方法、结果和讨论里，包含安全或伦理考虑和作者分工。正式项目报告采用 ICLR 提交格式，官方说明给出了各阶段页数、代码仓库与 AI 使用披露的要求。自学时可以把它们转成表格或短记录，保留任务和复现最需要的内容。 [Stanford 期末项目说明](https://cs329z.stanford.edu/project.html)

| 阶段 | 应能指给读者看的东西 | 怎样知道缺了什么 |
| --- | --- | --- |
| 提案 | 输入样例、初始数据、基线、明确的成功条件 | 评阅人能否独立判断一条答复是否合格 |
| 中期 | 一个可启动的原型、一条能复现的失败和最小验收 | 能否在未参与开发的环境里重跑一条任务 |
| 最终 | 固定题集、基线与候选配置、原始结果、失败分析和代码说明 | 看报告的人能否用同一份数据找回相同记录 |

准备报告时，先把依赖与数据来源写对。复制来的示例要保留许可和引用，虚构数据明确写明。若任务用真实用户记录，须把可使用的范围、用途、保留与撤回流程写清。团队成员可以各提交一条可复核贡献。例如一人维护评分器，一人负责运行配置，一人负责失败归因。说「我们都参与了」虽然简短，无法让别人定位哪项设计由谁完成。 [Stanford 期末项目说明](https://cs329z.stanford.edu/project.html)

## 项目做大之后还是回到可控的对照

如果第二阶段给预约系统接入 LLM，可以把可控例子转成一个更完整的项目。收集几种确实可能出现的输入，涵盖标准编号、设备俗称、相对时间、遗漏信息和自相矛盾的信息。标注要求基于应用规则，可以接受满足同一规则的不同表述。时间例子钉死基准时钟与时区，确保复现时「明天」指向同一天。测试每个状态应匹配的工具请求与最终外部结果，记录澄清是否真的补齐信息。

增加接入层之后，保留原始件。解析模块的字段可以单测。调用策略可以用工具替身重现错误。最终端到端测试一遍真正的运行。若端到端通过率下降，先在三个检查点看状态。字段是否正确？工具是否拿到了正确数据？模型是否把结果说准确？这样一条失败能区分解析、调用和生成。输出没说清楚时，也可能是验证标准含糊，不能立刻用它证明某个模块有错。

做公平对照时，让 baseline 和候选使用相同题集、环境与评分器，并说明是否使用同一模型和预算。调整预算本身也是一个实验变量。一个版本大幅增加重试次数后完成率提高，要同时披露用户等待和总消耗。统计多次尝试时，优先列出每题的尝试与成功次数。若允许选择多份输出中的一个，说明谁选择、能看到什么验证信息。只报告最好的几次，会让人高估实用性。 [官方评测课件](https://web.stanford.edu/class/cs329z/slides/lecture13.pdf) · [官方模型裁判课件](https://web.stanford.edu/class/cs329z/slides/lecture15.pdf)

复查报告时，可从一个失败标签回到具体记录。比如「合法查询却无可用答案」这一类，是否能找到被测输入、模型返回、调用参数、受影响的数据行与评分器版本？如果只能看到汇总图，证据链还有断口。相反，完整保留原始记录也不等于适合对外共享。报告可公开脱敏样例和固定数据，生产中的个人信息应留在受控环境。发布代码时提供复现所需的最小权限，让别人能重跑评测，而不接触真正的用户账号。

## 练习一｜加一道用例验证边界的可信度

增加 `("invalid_after_midnight", "S1", 23, 25, "invalid_interval")`。当前例子的时段限定一天内，因此所有配置都应得到正确的拒绝。把预期通过数同步更新为 6、7、7、9，组合版应达到 9/9。再增加一个设备编号合法但台账不可用的样本。现有脚本无法表达查询失败，预期要先扩充接口状态，再新增验证规则。不要把空记录和查询错误共用同一个返回值。

## 练习二｜写一段能复查的结果分析

给四个版本各写一行，说明运行版本、改动、输入、通过数和原因。重点跟踪 `alias_busy`。它从「不认识设备」到「认识但漏掉冲突」，再到「认识且正确拦住冲突」。重跑时验证两种设定是否保持同一批数据，说明结果只针对合成任务。最后补一句正式系统需要另测的限制，例如真实日期、跨时区、权限与并发写入。这样你的报告既能证明做过什么，也能让人看到还没有验证什么。
