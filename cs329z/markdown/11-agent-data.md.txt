# 第 11 讲｜Agent 需要什么数据

[课程索引](/cs329z/review/) · <a href="/cs329z/markdown/11-agent-data.md.txt" download="11-agent-data.md">下载 Markdown</a>

2026 年 10 月 28 日 · 根据 Stanford 公开课件整理。 [第 11 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture11.pdf)

假设学校的设备借用助手把「周五上午借一支无线麦克风」办成了「周四领一支有线麦克风」。只保存最后一句答复，以后很难判断系统在哪里走错。把用户请求、库存查询、工具返回和最终预约记录串起来，就能分辨它是读错日期、选错设备，还是没处理好工具返回的冲突。

## 把一次操作录下来，再把场景做成能重跑的题

**轨迹**是一次运行的记录。它包含模型收到的任务、调用过的工具、环境的回应和最后的提交。在用轨迹做监督微调时，工具返回通常用作上下文，学习目标是示范中模型做出的输出，例如看到缺少归还时间后发起追问。训练数据要明确哪部分是模型的动作，哪部分是它观察到的事实。

**可运行环境**包含任务、初始状态以及判定成功的办法。给助手同一份库存和预约表，恢复表的初始状态，它就可以重新尝试。用这些环境做强化学习时，可以按预约记录是否符合请求给反馈。评测也可以使用可重置的环境，但要另外留出没有参与调试或训练的案例。 [第 11 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture11.pdf)

课件把数据来源分为人类示范、从已有材料提取、合成任务、合成轨迹，以及模拟用户或环境。看一条数据能否拿来用，得先问它保留了多少真实操作的约束。例如，人工示范可以补上「库存不足时先问对方是否接受替代品」这类判断，合成环境则便于批量测试日期、时间和库存的组合。模拟器如果一直让预约写入成功，跑得再多，也覆盖不到写入冲突。

## 把有代表性的失败放回测试

一条有用的数据反馈路径是保存失败，核对成功标准，修正系统，然后用同类案例重新检查。修正时看到的原例可用于调试，另留同类的新例用来检验改动能否迁移。评分只查答复里有没有「预约成功」，系统很容易在数据库根本没有新记录时拿到满分。 [Shreya Shankar 的数据反馈循环](https://www.sh-reya.com/blog/ai-engineering-flywheel/)

## 一条轨迹要能还原从哪里开始走错

拿另一条请求试着记一遍。用户要借无线麦克风，周五 09:00 到 11:00。无线设备 M01 在 10:00 到 10:30 已有人借，另有一支有线设备 M02 空闲。系统把「无线」登记为硬约束，把「周五」解析到一个确定的日期，查询时带上完整区间。此时工具只给出了冲突和库存事实，系统还不知道用户愿不愿意换成有线。合格的下一步可以是说明冲突、给出其他无线设备的可借时段，或问用户是否接受有线。

把记录拆到足以判断问题发生在哪个环节。工具调用参数里的时间写错，是调用前就找错了东西。参数正确，但库存工具漏掉中间半小时的预约，是工具实现的问题。工具准确返回冲突，系统却未经同意改借有线，问题发生在它根据结果决定下一步时。库里最后还没有记录，助手却说已经办好，则是完成状态的判断出了问题。把四种错误全归到「回答不对」会把调试方向混在一起。

| 一次执行里记录什么 | 从记录里能回答的问题 |
| --- | --- |
| 请求、场景标识、初始库存版本、约束 | 这轮拿到什么信息，跟上次跑的是不是同一道题？ |
| 工具名、参数，以及调用前的授权或追问结果 | 系统究竟查了哪天，用户有没有同意换设备？ |
| 独立记录的工具返回和错误类型 | 查到了冲突、遇到了超时，还是工具报成功但没提供编号？ |
| 终止原因、最终答复、预约表变化 | 这轮是正常完成、停下来等人，还是用完步数？实际动了哪些数据？ |
| 模型、提示、工具和评分器的版本 | 这次结果能和哪次比较，出现差异时哪些部件可能参与了变化？ |

模型输出和真实环境结果应分开保存。比如同一句「已预约」，既可能出现在写入成功之后，也可能出现在工具超时之后。只看这句文字无法确定哪个结果发生了。要重放某段对话，可以用记录下来的工具返回，保持当时的观察。要重跑整个任务，则要恢复环境，让工具再执行。前者适合检查给定观察下的下一步决策，后者才能看到换日期策略或修改库存查询后的影响。

### 给模型模仿的动作需要和实际接口对得上

监督微调使用的轨迹通常会把用户、系统和工具消息作为输入条件，把助手动作作为训练目标。假设示范中在发现冲突后调用了 `ask_user`，而部署时只有输出文本和查库存两个办法。模型把示范学得很像，照样可能调用不存在的工具。所以整理数据时要保留接口版本和参数定义。换了一批工具，可以对齐真能对应的动作。对找不到等价动作的轨迹，先保留作分析材料，再用新工具重录示范。

强化学习用到可重跑的环境。一次任务可以产生多条试跑轨迹，系统按结果给分，再用奖励更新模型。评分信号可以是数据库里的结果、通过条件组成的量表，或人工偏好。代码容易反复检查具体记录，覆盖范围取决于你写了哪些条件。人工有机会看出含糊请求里的真实意图，但评分标准仍需要校准。对「借用结果正确」和「解释清楚」最好保留不同字段，让两类问题都能被看到。课件用一张图把可运行环境、多次试跑、轨迹筛选与奖励更新串在一起。 [第 11 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture11.pdf)

## 数据来源决定你容易漏掉哪类情况

人工示范的优势是能带上现场判断。例如值班员看到临借用户没写归还时间，通常会先问什么时候能还，免得占住下一场活动需要的设备。要让示范真的有用，应记下当时能查到的信息，并让不同值班员处理边界请求，再核对哪里是一致的规则、哪里仍有争议。有时人顺手做了一个没记录的口头确认，抄下点击步骤也无法直接复现。

从已有材料提取数据适合快速构建案例池。比如把问题单和修复后的测试结果拼起来，可以得到可练习的编程任务。把设备值班手册变成情景题，可以梳理哪些信息要追问。材料常缺少运行当时的状态。手册说「选择另一台设备」只能给方向，还要补原来有哪些设备、哪些正在借，才有可执行的题。引用现有材料也应保留来源，避免把过期流程误当成现行流程。

合成任务可以遍历具体变量。围绕一支设备，生成库存充足、全时段冲突、部分重叠和没人预约但设备维修四种情况。每题同时生成环境和核对条件，并用一份参考操作验证可解性。合成轨迹则从已经存在的场景出发，让模型示范查找、追问或完成借用。合成任务测有哪些情况可练，合成轨迹回答某种情况下可以怎样做。两者都要抽查题目和结果能否对应上。例如让同一个模型既生成有缺陷的请求，又自评「完全满足」，可能把问题直接带进数据集。

模拟用户可以把同一场景改写成多轮对话。若预设的模拟用户总主动说出归还时间，评测就不能区分助手会不会主动追问。给模拟用户掌握的信息设边界，同一题保留一句话用户和多轮用户，检查它有没有提前泄露答案。模拟环境也要产生真实需要处理的结果，例如可预期的校验错误和有上限的重试场景，并明确哪些实际副作用没有模拟。课件将模拟器的好处和偏差一起讨论，系统能学到环境给出的反馈，也会学到环境里碰巧被简化的部分。 [第 11 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture11.pdf)

## 给数据回路留出能检查的入口

一个可以从小处开始的做法是每周挑几条代表性的错误，把错误与要验证的条件配对。对于这次有线和无线混淆，检查最终预约表中的设备类型，还应看未获许可时有没有形成预约。修复时先回放原例。如果原例通过，再拿保留的不同日期、不同设备、不同说法检查泛化。对工具超时这类经常出现但实际原因不同的错误，可以记录一次原始失败的原因标签，有些是网络，有些是权限，有些是工具协议问题。不要为了把所有例子装入同一类而抹掉原因。

测试切分应考虑场景来源。若从一个值班手册条款生成了多种同义问法，把原句放训练、同义句放测试，往往得到的是对同一规则表述的熟悉度。想测新校区能否复用，要把整个校区的数据留作一组。想测新工具能否复用，另留工具版本和返回结构发生变化的场景。明确想测哪种变化，然后按来源、环境、版本或时间划分，能减少「换了句说法就算新题」的问题。

为了让以后的人复查一条数据，给任务和轨迹留 ID。任务文件注明初始状态版本、预期结果和评分器版本。轨迹另存尝试 ID、来源和最后状态。同一个任务的失败与成功都指回原始场景。要提交清洗后的材料，写清删除了什么字段，关联用随机标识时也保留必要的时序。借用记录里的账号、联系方式或与问题无关的日志不会帮助学会检查冲突。要测的只是同一个人的一致性时，使用虚构标识即可。

课件还提醒，模型可能学会对上评分器的习惯，或者过度适应训练脚手架。例如训练环境把「没有报错」当作成功，模型可能反复走最容易返回成功的工具路径。训练日志里所有库存错误都叫 `unavailable`，换实际环境遇到权限不足和库存冲突时，模型也可能当作同一种错误。让评分独立核对环境，并在定义清楚的环境间做对照，更容易知道改进是否停留在一个接口上。 [第 11 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture11.pdf) · [Shreya Shankar 的数据反馈循环](https://www.sh-reya.com/blog/ai-engineering-flywheel/)

数据飞轮要能看出「修了评测」和「修了执行」的区别。例如旧版把等待用户确认当失败。修正这个评分定义后，先拿冻结的旧运行重评，看看以前漏算的合理等待占了哪些案例。调整模型提示后，再用同一批题全量重跑，比较实际预约和追问有没有变化。前一次改的是对同一批行为的计分方法，后一次改的是行为本身。把两个实验分别记录，才知道新旧通过率能不能直接比较。若新一批用户请求变得更复杂，再抽样核对目前的评分标准还能不能覆盖最常见的真实需求。

一次失败会有多个标签，但需要知道哪个是最先出现的。例如解析「下周五」时算错了日期，之后查库存和写入都能在错误日期上顺利完成。如果只给最终结果贴上「库存管理失败」，下一轮可能去改本来正常的工具。在复查表里可以分开记失误首次出现的步骤、后来有没有纠正、最终状态受到什么影响。这样一条轨迹就能同时服务于模型行为改进和系统故障定位。

## 练习 1｜给一条成功轨迹加上失败对照

准备两个设备和一张预约表。无线 M01 周五 10:00 到 10:30 已被借出，有线 M02 空闲。用户要无线，区间 09:00 到 11:00。写一条手工轨迹，包含查询参数、返回冲突、提出替代选项和用户明确同意。环境记录里的新预约应只在同意之后出现，设备编号应对应用户同意的那个选项。再做三个反例，分别删去同意、保持预约表为空但说已预约、改写成错误时段。

**核对办法**。用同一份初始预约表手动执行四次。只有完整示范通过「完成借用」检查。删去同意时表应保持原样，状态记为等待确认。空表却说已预约、写入错时段各应产生明确的检查失败原因。保留四次的最终状态与文字答复，看同一条「已预约」会不会被评分器误收。

## 练习 2｜从同一次失误造出互不串题的材料

取「部分重叠被误判为空闲」当作工程问题，写出一条用于调试的轨迹、两条用于检查工具的固定输入，以及两条训练时不公开答案的评测任务。开发例可以用 10:00 到 10:30 与 09:00 到 11:00。评测例改成另外的设备、时间比例和说法，其中一个改成首尾相接，明确约定结束时刻可以接着开始。让连续时间解释和数据库状态检查各有一个落点，方便确定问题出在哪层。

**预期结果**。重叠场景返回冲突，首尾相接可用。调试例改完后可以继续保留为回归用例。两份评测任务在确定改动之前应保持封存。即使最后它们都通过，报告也只说验证了这两个边界，不把覆盖范围延伸到跨时区或并发写入。

下面是只核对两个时段是否重叠的最小 Python 例子，可用来检查练习里的预期。例子假定所有时段都在同一天，用从午夜开始的分钟数表示。正式数据需要保留日期和时区，也要处理设备状态和跨日预约。

```python
from copy import deepcopy

INITIAL_BOOKINGS = [
    {"device": "M01", "start": 600, "end": 630},
]


def is_available(bookings, device, start, end):
    if not 0 <= start < end <= 24 * 60:
        raise ValueError("expected a nonempty same-day interval")
    return not any(
        row["device"] == device
        and start < row["end"]
        and row["start"] < end
        for row in bookings
    )


cases = [
    ("M01", 540, 660, False),  # 09:00–11:00 contains 10:00–10:30
    ("M01", 615, 645, False),  # 10:15–10:45 partly overlaps
    ("M01", 630, 660, True),   # 10:30–11:00 only touches the boundary
    ("M02", 540, 660, True),   # a conflict on M01 does not block M02
]

for device, start, end, expected in cases:
    actual = is_available(deepcopy(INITIAL_BOOKINGS), device, start, end)
    assert actual == expected, (device, start, end, actual)
    print(device, start, end, actual)
```

四条应按顺序输出 `False, False, True, True`。这段代码只检查所选设备，最后一条可用也只说明 M02 没被占用。若实际需求是无线设备，还需要另一项设备类型检查。把这两个条件分别记到结果里，之后才知道失败需要修时段逻辑，还是修设备选择逻辑。
