2026 年 11 月 9 日 · Stanford 课表列出 Diyi Yang 主持的 Andrew Ng 对谈。截至 2026 年 11 月 24 日，课表未列这场对谈的课件或视频。本页为讨论准备，依据 Andrew Ng 主讲的公开课程介绍。 [Stanford 官方课表](https://cs329z.stanford.edu/) · [DeepLearning.AI Agentic AI 课程](https://www.deeplearning.ai/courses/agentic-ai)

假设你要让助手用自然语言处理校园设备借用。最简单的做法是让它提取时间和设备，再由程序按固定顺序查库存、给出选项。它遇到库存冲突时，可以把选项交给用户，也可以在授权范围内继续寻找替代设备。用这个例子读 Andrew Ng 的公开课程大纲，可以把反思、工具调用、规划和多 Agent 协作还原成具体的流程选择。

## 讨论题

1. **哪里需要模型决定下一步？** 查库存和建预约都有明确的接口。列出哪一步需要理解「周五早一点」，哪一步可交给确定性规则核对时间重叠。再说明一个值得加入动态规划的情况。
2. **怎样验证第二轮检查有帮助？** 让第二轮只检查设备类型、借用时段和用户的原要求。比较加入检查前后的任务结果，同时记录额外耗时。看它修掉了多少错误，又改坏了多少原本正确的答复。
3. **什么时候值得拆成两个 Agent？** 可以考虑将政策查询与库存查询分开并行。先说清两边要交回哪些字段，再跟单个助手依次查询比较。除了延迟，还需要观测合并冲突和调用次数。 [Andrew Ng 的课程介绍](https://www.deeplearning.ai/the-batch/check-out-our-course-on-how-to-build-ai-agents)

## 把抽象模式放回一个具体流程

校园设备借用的难点并不都在理解文字。学生说「周五上午给社团留一台投影仪，讲完还」，可能漏了结束时间。库存随时变化，设备可能维护，借用资格也由活动类型和账号决定。模型可以提取大意，再把确切信息交给程序核对。要让读者能跟着设计，可以先按顺序写下系统如何记录请求、找到候选、等待确认、写入预约并回传编号。每次经过这个状态，可以观察哪一步需要新信息，以及是否已经造成外部修改。

Andrew Ng 的公开课程把设计模式拆为反思、工具调用、规划与多 Agent 协作，并列出任务拆分、评估和错误分析。读这几部分时，可以把它们看成一组可独立试验的手段。对于借用助手，每种手段都可以只接在需要的位置，再用同一批用例判断多出的复杂度有没有改善真实问题。 [Andrew Ng 公开课程大纲](https://www.deeplearning.ai/courses/agentic-ai) · [Andrew Ng 的课程介绍](https://www.deeplearning.ai/the-batch/check-out-our-course-on-how-to-build-ai-agents)

### 反思需要比原答复多一点可检查的信息

设想第一版答复说「已为你预留一台投影仪，周五 10 点领取」。第二轮检查时，要拿到用户原请求、工具真实返回的候选清单，以及与本轮有关的预约编号。若清单只有候选而数据库没新增记录，就把答复修成「有候选，需要确认后才能预订」。若同一模型只拿到原答复，再被问一句「是否正确」，它没有新的证据判断预约是否存在。

可以把反思写成检查表。查「时段齐不齐」时，对照原请求与实际可用时间。查「是否已经办好」时，先看写操作结果。查「是否有更简洁的说法」时，才看文本是否容易读。前两项有客观依据，第三项比较适合人工或模型辅助检查。一次反思只改已经发现的问题，避免把原本正确的约束一并改掉。比较时分别记下修掉的坏例和误改的好例。只有在读过同一批用例后，才能知道二次检查的价值属于事实核验、语言改善，还是两者混在一起。 [公开课程的 Reflection 单元](https://www.deeplearning.ai/courses/agentic-ai)

### 工具边界决定了反馈是否可用

工具调用让模型接触库存、借用规则和当前预约。给借用助手两类工具就能做许多事。查询方法接受设备类型和时段，输出候选、冲突和库存版本。写入方法接受具体候选、确认凭据和请求编号，独立校验是否仍可借。查询成功只说明当时看到的库存情况。等用户确认后再写入，库存可能已经改变，所以写入仍需要重新验证。

工具返回也可以设计得利于下一步。把「时段冲突」「参数不完整」「权限不足」「服务暂时不可用」放到独立的状态码，系统便可按不同情况选择回答、追问或停止。在没有预约编号且状态未知的情况下，可以通过请求编号查询既有结果，避免重复创建。写操作最终由运行时检查权限，模型提出的参数只代表它建议怎么做。这样可以试验新的提示词，同时保住系统的基本行为约束。

### 规划主要影响系统在遇到变化后怎样继续

一个固定的流程可以完成常见请求。提取完整时段后核对库存，给出候选，拿到确认再提交。若用户可以接受同功能替代品，还要比较转接头和借用地点，就有动态规划的空间。助手先查本楼库存，没找到后查同类替代品，再看别处能不能在活动前取到。此时新增查询仍要受条件限制。例如用户说只在本楼取，就没有必要继续查另一校区。

规划通常还需要区分一次拟定和边做边改。把所有步骤先写出来，容易在工具失败或用户补充限制后走偏。可以给每一步写清输入和期望结果，拿到真实观察后更新计划。遇到要求变化时，检查前面的动作是否还能保留。用于确认的库存快照过期，可以重新发候选，请用户看是否接受。用一个固定的最大查询步数，能防止在各种替代品之间反复搜索。公开大纲把计划的生成、执行和高自主任务放在同一模块，可用这个例子先找出两者之间的接口。 [公开课程的 Planning 单元](https://www.deeplearning.ai/courses/agentic-ai)

### 多 Agent 的代价通常出现在交接处

假设政策助手负责资格，库存助手负责查可用设备。两方可以并行读不同信息，主流程收集结果后统一处理确认。想让交接可核对，就不能只要求它们各写一段自然语言。政策方面至少交回借用资格、使用的规则版本和补充材料。库存方面交回设备、可用时段、地点和快照版本。若政策说个人不能借该类设备，库存即使查到实体空闲，也不能直接推荐给个人。合并逻辑要明确哪一方提供哪种事实，以及不一致时向谁追问。

如果当前只需要一次政策判断和一次库存查找，普通代码同样可以并行查询，再由一个助手解释结果。要比较两种架构，固定相同的工具和用例，记录响应时间、模型调用次数、字段缺失和相互矛盾数量。两支 Agent 的输出各自都合理，最后仍可能因时间表达或规则版本不统一而失败。把整条交接记录保存下来，才知道多 Agent 减少了哪些等待，又增加了哪些同步问题。 [公开课程的多 Agent 单元](https://www.deeplearning.ai/courses/agentic-ai)

## 把评测拆到能直接修问题的位置

设想版本 A 做固定流程，版本 B 在部分查询后加入一次反思。测试的用户请求包括资料充足、缺结束时间、指定设备已借出和库存发生变化四种。端到端结果用预约表和最终答复核对。若版本 B 确实少说了几次「预约成功」，还要回查第一轮有没有建成预约、复核有没有拿到真实工具证据、第二轮回复是否准确展示状态。只统计最后是否出现某个词，就不知道错误在哪层被修掉。

可以给每一轮记录以下几项。缺信息时是否正确地追问，合规候选是否被恢复出来，写入的对象和时段是否匹配，重复请求是否只产生一条预约。再记录用户看到的耗时和实际调用次数。这样，工具组件变慢但最终成功率提高时，你可以按任务类型考虑是否只在含糊和冲突场景启用第二轮。公开课的错误分析内容强调从系统结果回到具体组件。适合做练习的场景越小，越容易看清改一处带来的效果。 [Andrew Ng 公开课程大纲](https://www.deeplearning.ai/courses/agentic-ai)

| 需要处理的情况 | 起步方案 | 核对标准 |
| --- | --- | --- |
| 请求完整、政策稳定 | 固定流程查询 | 候选设备与整个时段都匹配 |
| 缺少结束时间 | 提取后进入追问 | 能说明缺少什么，未改预约表 |
| 某设备在用户允许的条件下可替代 | 让系统在限定范围内找替代候选 | 替代方案符合类型、地点和时段要求 |
| 用户已确认，但库存版本变化 | 重新校验后反馈 | 不提交过期候选，告知情况发生变化 |

### 如何进一步准备对谈讨论

从一次失败里提出一条可以靠证据判断的问题。比如「遗漏归还时间的情况，加入反思能否减少随意补全？」这里可以对照只靠一次模型提取、程序强制检查缺失字段、加入二次模型复核三种方案。对每类方案都测试 4 条缺字段和 4 条字段齐全的请求。只讨论召回了多少错误不够，还要看正常请求里多出了多少不必要的追问。想交流工程选型时，带着例子和衡量方式，会比只问「哪些 Agent 设计最好」更容易深入。

如果问题是何时把固定流程交给模型，需要先定义允许它决定哪一类事情。选择查询参数和决定是否对外发出动作是两个不同的权限。借用助手可以自主判断接下来要查无线还是同类设备。写入则需要系统认可的确认记录。把这些决定拆开讨论，既能比较性能，也能比较错误后果。

把纸上结论带回工程时，还可以提前写一条退出规则。举例来说，同样一轮增加反思后，如果只让正常请求多等了几秒，冲突解释依然出错，就先回头看执行记录里有没有冲突证据。只有拿到这个字段后才适合继续调复核提示。用能观察、能撤回的小改动检查设计，比整套替换后再猜哪项设计起作用容易。

## 练习 1｜画出固定流程和允许追问的流程

选两条请求，一条资料齐全，一条缺少归还时间。给每条写出模型看到的请求、查工具前的状态、至少一个预期的工具输出。在纸上画两套流程。固定流程允许拒绝继续并提示缺字段。允许追问的流程要求拿到明确时间后才发出下一次查询。再加一种工具返回两台合规投影仪、用户没有指明型号的情况。

**检查结果**。资料齐全时，两套流程都能给出可用设备。缺少归还时间且无法判断冲突时，已有预约保持原样。话术可以自然，但要说明到底缺的是哪个字段。出现两个同等候选时，可以按事先约定选一个或让用户选择，记录选择依据即可。对照流程图检查「查到候选」和「预约写入」有没有被你当成同一步。

下面用 Python 把流程中允许执行的动作写成几个固定分支。输入是已经提取并核对过的字段，完全不含模型调用。练习可以把同一张输入表分别交给程序规则和一个手写的模型输出样例，照着表里的预期查差异。

```python
def decide(request, latest_version):
    if request["end"] is None:
        return "ask_end_time"
    if request["start"] >= request["end"]:
        return "ask_valid_interval"
    if request["candidate"] is None:
        return "search_inventory"
    if request["candidate_version"] != latest_version:
        return "refresh_inventory"
    if request["confirmed_candidate"] != request["candidate"]:
        return "ask_confirmation"
    return "submit_booking"


ready = {
    "start": 600, "end": 660, "candidate": "P02",
    "candidate_version": 2, "confirmed_candidate": "P02",
}
cases = [
    ({**ready, "end": None}, "ask_end_time"),
    ({**ready, "end": 590}, "ask_valid_interval"),
    ({**ready, "candidate": None}, "search_inventory"),
    ({**ready, "candidate_version": 1}, "refresh_inventory"),
    ({**ready, "confirmed_candidate": None}, "ask_confirmation"),
    (ready, "submit_booking"),
]
for request, expected in cases:
    result = decide(request, latest_version=2)
    assert result == expected
    print(result)
```

最后一条只给出「可尝试提交」。是否提交成功仍要由写入工具重新检查。真实系统的确认要关联完整预约信息，可以绑定设备、日期、时段和用户，避免只凭设备编号就沿用旧确认。再给程序增加一个规则变化的案例，确认遇到过期候选时仍会先刷新数据。

## 练习 2｜设计一轮能解释结果的反思对照

找三条原始答复给复核员。A 把「找到候选」说成「成功预约」。B 已经准确告诉用户需要确认。C 预约确实写成功，但答复把归还时间写错。每条都配一份明确的预约表和工具返回。设计两个复核条件，一组只看原答复，另一组看同样答复以及对应的环境证据。提前规定允许改状态和时段，不根据长短和语气给分。

**预期核对**。A 应改成等待确认，B 保持原意，C 应按预约表改正时段。只看原文时，A 与 C 缺少验证依据，可以标为证据不足。把两组能纠正的错误数、误改正常答复数和无法判断数并列，写下缺失的证据。若后来真正接入模型，再固定模型版本和评分规则运行。纸笔练习只能核对设计是否正确，不能据此声称某个模型会稳定达到这些结果。
