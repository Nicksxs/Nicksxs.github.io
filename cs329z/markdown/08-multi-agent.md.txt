# 第 8 讲｜多 Agent 的编排、交接与协调

[课程索引](/cs329z/review/) · <a href="/cs329z/markdown/08-multi-agent.md.txt" download="08-multi-agent.md">下载 Markdown</a>

授课日期 2026 年 10 月 19 日

学生想在下午借相机，并预约一间能做录制的场地。查设备和查场地可以同时开始。等两边返回后，还要算出都可用的时段，向学生确认，再处理别人抢先占用的情况。如果让两个 Agent 各自推进到底，它们或许能更早报出空档，也可能各自约了不同的时段。决定怎样分工之前，先把需要共享的信息和最终写入的责任讲清楚。

这堂课从三个角度拆解多 Agent 系统。编排决定谁去做哪段工作，通信决定怎样传递请求和结果，协调则管依赖、状态、工作区和冲突。团队可以复用同一个模型，也可以给不同职责配置不同模型和工具。关键在于成员各自有决策和执行的范围，同时围绕同一个用户目标协作。 [Stanford 第 8 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture08.pdf)

## 从单 Agent 的依赖关系出发

先把用户请求画成几步。解析日期和时长后，查询库存、场地和资格。拿到结果后求交集，给用户预览。确认后重新验证可用状态并提交。这条链上，每个步骤的输入来自哪里，会决定它能否提前开始。库存查询如果仅依赖已确定的日期，就能和场地查询重叠。资格查询如果还需要最终的设备编号，就要等候选设备确定。提交依赖确认和最新状态检查，前面两项做得再快，也无法让最后一步提前发生。

可拆任务一般有几种收益。某些分支读不同数据，彼此可以在独立上下文里并行。专项成员只需要熟悉一种工具的字段和错误处理。开放式研究可以分配不同假设，再统一汇总证据。分工同时带来复制上下文、委派、返回结果、检查中间产物和处理重试的开销。延迟由最长依赖路径以及交接、排队、合并等开销共同决定。总成本还要把各分支的 Token、工具调用和编排调用相加。在讲义里的虚构预约场景，两个查询无需共享执行步骤，可以先尝试让一个 Agent 并行调用两项工具。只有分工能解决已有瓶颈，再引入额外的决策者。 [Stanford 第 8 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture08.pdf)

反过来看一组串行依赖。管理员要求「找到已确认的相机预约，把原时间和可替换时段列出来」。查询可替换时段要先知道原订单使用的设备、日期和资格。两个成员各自猜其中一半，会重复查询或者依照不同规则推进。此时单 Agent 或者一段明确的串行工作流更容易保持约束一致。如果操作争用同一份库存，还要限制实际写入者，或者在服务端协调并发。增加成员并不会增加最后一台相机的库存。

Kim 等人在固定工具、提示和计算资源的对照中测量了单 Agent 和四种多 Agent 架构。论文中，可分解的金融推理在某些配置下从分工受益，强串行的规划任务则出现退化。工具密集任务的通信和交接可能进一步抬高开销。论文给出的是特定任务、模型和配置下的经验结果。移植到自己的系统时，需要按任务结构分组测量，尤其要把强单 Agent 留在基线里。 [Towards a Science of Scaling Agent Systems，v3](https://arxiv.org/abs/2512.08296v3)

## 编排拓扑怎样改变信息和决策流

| 形态 | 一次任务如何推进 | 适合的边界与代价 |
| --- | --- | --- |
| 独立计算后汇总 | 各成员拿到分支输入，各自完成，汇总者最后读产物 | 适合分支之间无需交换中间结果的任务。可以并行，也要给汇总器处理缺项、重复和冲突的规则。 |
| 中央编排 | 编排器接受任务、派发工作、核对回传，再决定下一步 | 动态拆分和恢复比较集中。任务多时，编排器本身会占用模型调用、上下文和排队时间。 |
| 去中心协作 | 成员经由消息或共享板协商，并可领取或分派后续工作 | 灵活度高，适合存在多种探索方向的工作。需要明确任务权属、同步方式和停止条件。 |
| 混合编排 | 总体计划、写入和验收由中央控制，相关成员可直接协调局部依赖 | 能减轻部分逐级传话的负担。要明确定义谁可以直连，以及局部决定怎样被记录到总体状态。 |

表中每一种都能用来处理同一份预约请求，区别在于把哪些决定交给谁。查询对象已知时，独立分支返回相机窗口与场地窗口就够了。如果场地临时闭馆，需要查备用场地，再根据备用场地的接口核对相机配件，中央编排器可以按返回状态创建下一项任务。若设施系统和设备系统必须一起排期，可以让对应负责人交换几个结构化候选，再把选择交给协调方。把这项预约做成开放的通用群聊，会增大受影响的上下文和冲突范围。 [Stanford 第 8 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture08.pdf)

编排还可以根据任务改变团队结构。课件举了 DyLAN，先用初步试验根据成员在解决任务过程中的贡献估计重要性，选出适合该类任务的成员。处理新输入时，成员之间的协作和参与程度再根据问题调整。这个做法提醒我们，成员选择和消息拓扑是可调的实验变量。自己的预约系统可以用简单的分类先决定是否需要场地 Agent，再从最终证据核对分类分流有没有漏掉所需输入。教研系统里某个协作机制的得分提升，不能直接代替这项业务测试。 [DyLAN 论文](https://arxiv.org/abs/2310.02170v2)

## 用清楚的契约交接

### 谁负责继续和用户交互

把 Agent 当作工具调用时，调用者保留控制权。比如主 Agent 发给场地 Agent 日期、候选时间和所需房型。场地 Agent 查完后返回可用窗口、来源和版本，主 Agent 负责合并库存结果并和用户确认。主 Agent 还要决定查询失败后是否换工具或明确告知无法判定。被调用成员可以只拥有读取场地资料的权限。

Handoff 转移当前交互的控制权。用户问到特殊器材资格时，主 Agent 可以把后续问题交给资格专员。接手方直接继续收集材料、澄清条件，再按应用规则推进。交接需要带过去的状态包括用户目标、已确认的日期、前面获得的证据、未解决问题以及仍然有效的限制。否则专员会重新询问，或者把表面上相似的请求当成一项新预约。这里转移的是控制权，服务端仍要检查接手者能读哪些资料、能否调用某项写入接口。 [Stanford 第 8 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture08.pdf) · [OpenAI Agents SDK 的 Handoff 说明](https://openai.github.io/openai-agents-python/handoffs/)

应用可以给交接约定一组字段，分开记录已经观察到的事实和接手者应做的工作。例如 `request_id` 和 `date` 限定本次任务，`evidence` 是已读资料及版本，`pending` 是接手者要回答的问题，`confirmation_state` 表示用户是否确认过某一份预约预览。能够传递这些字段就保留它们，同时避免把上一段聊天的个人信息和内部凭证全部复制过去。若用户已改日期，要作废旧预览和旧确认，重新运行依赖该时间的分支。

### 消息发到哪里

AutoGen 把可对话 Agent 作为组件，允许开发者用程序和自然语言来组织互动。顺序模式可以让调查者交给审查者，集中模式可以让子成员通过上级分发和回报，群聊模式允许成员共享一定范围的对话内容。这些通信方式可以组成更复杂的流程。比如两个成员独立查库存和场地，结果汇总后再交给审查者检查范围和日期，比把所有工具原始输出都转发给每个成员更容易复核。 [AutoGen 论文](https://arxiv.org/abs/2308.08155) · [Stanford 第 8 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture08.pdf)

共享消息板适合通过产物异步协作。一个成员发布一条带任务编号的结果，另一个成员读到自己等待的结果再继续。当多人写同一主题时，板子上的消息有发送者、更新版本和完成状态，接收者才能知道该采用哪一条。消息内容可记录承诺，对预约的更新还得落到负责判断状态的账本或服务中。某个成员在共享板写「改约已批准」，最多给其他成员一个待核查的说法。可执行授权应由记录真实用户确认的应用提供。 [Stanford 第 8 讲课件中的 Message Board 示例](https://web.stanford.edu/class/cs329z/slides/lecture08.pdf)

当设备和场地由不同服务或组织维护，A2A 提供跨系统的发现、任务状态和消息交换方式。Agent Card 描述服务能力、接入信息和安全要求。请求提交后可以获得任务标识，用来查询状态、订阅更新或识别返回的交付物。两个服务仍各有业务权限。设施 Agent 收到一条符合协议的消息后，要验证调用者是否有权读取对应房间。预约 API 则依据已登记的身份、任务范围和具体确认作出写入决定。任务状态到达「需要授权」，表示后续动作还要走应用定义的授权流程。 [A2A 协议规范，认证与授权](https://a2a-protocol.org/latest/specification/#7-authentication-and-authorization)

## 用账本、记忆和工作区协调执行

### 把进度从聊天里拿出来

多 Agent 系统聊天够活跃也可能没有进展。每位成员写一段文字说明自己的计划，团队仍需知道哪些前置已经完成、由谁负责更新、什么证据标志着可以进入下一步。课件介绍的 Magentic-One 由 Orchestrator 维护任务账本和进度信息。整体账本记录目标、事实和计划，进度账本用于判断当前是否推进、下一步要派给谁以及是否需要重新规划。遇到连续停滞时，应回看目标与剩余阻塞，而不是让成员再次重复相同请求。 [Magentic-One 论文](https://arxiv.org/html/2411.04468v1) · [Stanford 第 8 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture08.pdf)

从预约场景开始，账本可以只有下列状态。目标比任何成员自己的子任务范围更大，例如即使设备 Agent 已经查到相机，也要等场地和借用资格。并行读到的结果有独立的来源版本。提交只读经过确认的那份预览，并由具备权限的执行者调用。重试时，通过请求标识匹配同一个预约操作，避免把网络超时后的再次确认当成第二笔预约。

| 账本条目 | 所有者 | 启动条件 | 完成证据 |
| --- | --- | --- | --- |
| 解析预约范围 | 主 Agent | 收到有权限的用户请求 | 日期、时长、设备类别、房间范围齐全 |
| 查可借相机 | 设备 Agent | 解析完成 | 含来源版本的查询结果，或者明确失败 |
| 查场地与规则 | 场地 Agent | 解析完成 | 场地开放区间、所用政策版本和规则结果 |
| 合并并预览 | 主 Agent | 两路有效结果齐备 | 写入字段和可用时段的预览，附同一请求标识 |
| 确认并预约 | 应用服务 | 用户确认指定预览 | 通过权限、占用和幂等检查，得到持久记录 |

角色划分解决谁做哪项任务。资源划分进一步明确谁能写哪一段数据或哪一套文件。剩下的共享约束需要协商，例如两位成员提出不同时间范围时，要按哪份规则解决。若设备和房间属于两个服务，分别写入有可能只成功一半。系统要明确半完成状态以及怎样撤回、重试或请人处理，汇总者只在必要记录到齐后宣布完成。这个例子的 Python 练习用同一个内存服务模拟写入，因此可以把授权、版本检查和提交放在一个短流程里。

### 分开短期状态与跨任务经验

一笔预约的进展由账本和业务记录决定。历史经验可以让团队更早遇到正确的问题。G-Memory 把以往协作组织成三层图。洞见层抽象可迁移的经验，查询层关联不同历史任务，交互层保留细粒度的成员往来。新请求到来时，系统可以按查询的关联取回概括性的建议，也可以找出以往一段较精简的协作过程。对预约任务来说，高层经验可能指出「跨部门器材要核对两份政策」。查询层能定位近期跨部门个案，交互层留下当时是谁拿到了哪版规则。 [G-Memory 论文](https://arxiv.org/abs/2506.07398) · [Stanford 第 8 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture08.pdf)

经验是帮助下一次探索的材料。新订单是否还能借，要看当前库存。授权记录也要对应当前用户和本次预览。假设共享记忆里记着「周三下午可以用 B 室」，检索到它后只能据此决定优先查 B 室，不能跳过当天的开放状态。维护共享经验时保留来源和有效范围，可以减少某个 Agent 的判断错误逐轮扩散。群体探索希望产生多条独立候选时，也可以约定先独立取证，再看其他成员推断，降低过早跟随同一个答案的概率。

### 隔离编辑位置，统一验证集成结果

课程里的编码协作案例涉及工作区隔离。Git worktree 允许同一仓库拥有多个工作目录，在各自的分支或工作状态中改动。一个成员负责查询接口，另一个负责渲染预览，两人可以分别提交并运行局部测试。集成方要在统一基线下合并，再跑跨组件测试。若查询接口改成结束时间不含端点，预览代码仍把它显示成可占用的最后一分钟，两个提交可能改了不同文件，也会在业务语义上冲突。版本控制合并干净只能说明文本可以并在一起。 [Git worktree 文档](https://git-scm.com/docs/git-worktree) · [Stanford 第 8 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture08.pdf)

课件还提到并行构建 C 编译器的工程案例。随着工作集中到同一个复杂的失败上，成员重复处理与相互覆盖的风险增加。案例作者用已知可用的编译器处理大部分输入，再分别把选定范围交给新编译器，给调试工作创造可隔离的分片，同时用可反复执行的测试和共享任务记录追踪进展。类比到预约系统，如果失败集中在一个规则接口，先找能独立重放的故障用例，分派具体分支，再收回来做统一验证。 [Anthropic 工程案例](https://www.anthropic.com/research/building-c-compiler)

## 一次预约怎样通过并行查询到达写入

以下全部是虚构数据。请求 `req-27` 查询 2026 年 11 月 12 日下午能借相机和录制房间的一段连续 60 分钟。设备 Agent 报告相机 `CAM-07` 13:30–16:30 可用。场地 Agent 报告 `ROOM-B` 15:00–17:00 可用。两项都带当前状态的版本号。可共同使用的完整窗口是 15:00–16:30，示例从窗口起点取一段足够长的 15:00–16:00。预览展示两个资源、日期和时长，由用户确认这份具体内容。

这里的两条查询拥有相同的用户请求标识和日期。若版本没对齐，合并器至少要知道其中一份结果是否过期。这个练习给两种资源用同一个递增版本。真实系统里分别维护设备和场地版本时，可以分别保存和检查。用户点确认后，应用会核验执行角色、绑定的预览和提交时的状态。如果有人已经更改库存，旧预览应回到重新查询和确认环节。同一个已成功请求重试时，可以从已提交记录返回先前结果，不再创建新预约。

### 练习一｜复现延迟确认与重复提交

将代码保存为 `coordination_check.py`，运行 `python3 coordination_check.py`。它用顺序重放模拟事件竞态，并用内存结构表示认可的预览和持久预约的最小形态。先预测两个查询成员都请求写入、用户确认期间状态已变、客户端重试这三种情况下最终有几条记录。

```python
from dataclasses import dataclass, replace


def minute(value):
    hours, minutes = map(int, value.split(":"))
    return hours * 60 + minutes


def show(value):
    hours, minutes = divmod(value, 60)
    return f"{hours:02}:{minutes:02}"


@dataclass(frozen=True)
class Window:
    request: str
    date: str
    resource: str
    kind: str
    start: int
    end: int
    revision: int


@dataclass(frozen=True)
class Draft:
    request: str
    date: str
    resources: tuple
    start: int
    end: int
    revision: int


def propose(camera, room, duration):
    if (camera.request, camera.date) != (room.request, room.date):
        raise ValueError("mismatched query")
    if (camera.kind, room.kind) != ("camera", "room"):
        raise ValueError("mismatched resource type")
    if camera.revision != room.revision:
        raise ValueError("mismatched inventory view")
    start, last = max(camera.start, room.start), min(camera.end, room.end)
    if last - start < duration:
        return None
    return Draft(
        camera.request,
        camera.date,
        (camera.resource, room.resource),
        start,
        start + duration,
        camera.revision,
    )


class BookingStore:
    def __init__(self, revision, approvals=()):
        self.revision = revision
        self.approvals = set(approvals)
        self.by_request = {}

    def submit(self, actor, draft):
        if actor != "booking_service":
            return "forbidden"
        saved = self.by_request.get(draft.request)
        if saved is not None:
            return "already_confirmed" if saved == draft else "request_mismatch"
        if draft not in self.approvals:
            return "confirmation_required"
        if draft.revision != self.revision:
            return "stale_view"
        for booking in self.by_request.values():
            same_day = booking.date == draft.date
            shares_resource = bool(set(booking.resources) & set(draft.resources))
            overlaps = booking.start < draft.end and draft.start < booking.end
            if same_day and shares_resource and overlaps:
                return "no_longer_available"
        self.by_request[draft.request] = draft
        self.revision += 1
        return "confirmed"


def main():
    request, date = "req-27", "2026-11-12"
    camera = Window(request, date, "CAM-07", "camera", minute("13:30"), minute("16:30"), 7)
    room = Window(request, date, "ROOM-B", "room", minute("15:00"), minute("17:00"), 7)
    draft = propose(camera, room, 60)
    assert draft is not None
    assert (show(draft.start), show(draft.end)) == ("15:00", "16:00")
    assert propose(camera, room, 120) is None
    print(f"proposal: {show(draft.start)}–{show(draft.end)}")

    before_confirmation = BookingStore(7)
    current = BookingStore(7, [draft])
    changed = BookingStore(8, [draft])
    checks = (
        ("camera_agent", current.submit("camera_agent", draft), "forbidden"),
        ("room_agent", current.submit("room_agent", draft), "forbidden"),
        (
            "without_confirmation",
            before_confirmation.submit("booking_service", draft),
            "confirmation_required",
        ),
        ("expired_view", changed.submit("booking_service", draft), "stale_view"),
        ("first_commit", current.submit("booking_service", draft), "confirmed"),
        ("retry", current.submit("booking_service", draft), "already_confirmed"),
        (
            "reuse_request_for_other_time",
            current.submit("booking_service", replace(draft, end=minute("16:15"))),
            "request_mismatch",
        ),
    )
    for label, actual, expected in checks:
        assert actual == expected
        print(f"{label}: {actual}")
    assert len(before_confirmation.by_request) == len(changed.by_request) == 0
    assert len(current.by_request) == 1
    print(f"saved: {len(current.by_request)}")


if __name__ == "__main__":
    main()
```

```text
proposal: 15:00–16:00
camera_agent: forbidden
room_agent: forbidden
without_confirmation: confirmation_required
expired_view: stale_view
first_commit: confirmed
retry: already_confirmed
reuse_request_for_other_time: request_mismatch
saved: 1
```

**核对结果**　成功路径恰有 1 条记录。两个查询成员都不能写入。当前版本变化使旧预览失效，重新提交同一份已确认预览只返回已有结果。把同一请求标识用于不同时间会被拒绝。若用户实际想变更预约，应启动对应的改约流程，重新展示并确认新版本。这里的脚本只验证顺序模拟的状态转移，受信身份和审批集合由测试事先给定。实际服务里要让记录写入、重复检查和占用检查受同一事务或等价的并发约束保护，并额外测试两个请求同时占用资源的情况。

也可将它用在交接单元测试。把场地 Agent 返回的日期改成下一天，保持其他字段不变，再调用 `propose`，应拒绝合并。把日期还原而将所需时长改成两小时，当前共同窗口不足，应返回空。两类情况的后续处理不同。前者去查接收了哪个请求或版本，后者应告诉用户可用时间不足，或者在允许范围内查其他时段。

## 怎样判断失败出在哪一层

Cemri 等人的 MAST 把观测到的问题按系统设计、成员间不一致、验收三类归纳。系统设计方面，要看分工、停止规则、资源边界是否清楚。成员不一致，要看交接时漏了什么，谁以为另一方会做哪一步，以及是否用到了互相冲突的版本。验收方面，要看成功标准、最终状态和报告是否一致。一个任务可能同时有多层问题。复盘可以沿时间线找最早缺失的证据，并记录后续错误怎样被它触发。 [Why Do Multi-Agent LLM Systems Fail?，v3](https://arxiv.org/html/2503.13657v3)

| 失败迹象 | 可以先查哪条证据 | 该修改哪一层 |
| --- | --- | --- |
| 两个成员都开始为同一资源提交 | 角色和工具权限、写入服务的调用记录 | 限定最终写入责任，服务端执行权限与占用约束 |
| 一个成员用本地 15:00，另一个按 UTC 跑查询 | 交接字段、两路工具入参以及原请求 | 固定时区和日期所在字段，关联请求版本 |
| 场地 Agent 写「应可用」，汇总方当成已确认 | 返回结构的状态值、版本、证据、汇总规则 | 把推断、实查结果和预览确认分为不同状态 |
| 用户看到预约完成，系统里没有预约号 | 最终写入回执、实际业务记录、结束条件 | 以事务结果和持久记录验收，查清未记录的错误 |
| 多次询问同一分支，始终等不到结果 | 账本的分配时间、消息发出/收到事件、重试计数 | 给异步任务跟踪状态，设定重试和终止条件 |

CooperBench 给两个编码 Agent 分配可以独立实现但合并时可能冲突的功能，再用真实仓库和验收测试测它们能否协作。在论文的设置里，协作结果总体低于同一个 Agent 独立完成两项功能。开放通信仍可能出现含糊或过晚的消息、没有遵守已约定的分工，以及对另一成员工作进度的错误假设。个别成功的协作会主动划分角色、资源或协商共同方案。读这类结果时，注意「能写两段代码」和「两个经手者能把改动集成成一个通过测试的版本」分别消耗了什么。 [CooperBench 论文，v2](https://arxiv.org/abs/2601.13295v2)

在本例中，成员之间能发消息只说明通信链路通畅。交接消息写明结果有效范围，并让总流程在两路证据齐全后和用户确认，才同时检查了协调和业务流程。复盘可以把试验的环境版本、真实读写动作、各方收到的消息和最终判定放在一起。如果几个成员指望对方调用查询接口，问题出在责任和依赖发布。若它们都按计划查询却拿到不一致的版本，要检查时序和数据一致性。若系统知道结果缺一项却宣布成功，要改结束与验收条件。

### 练习二｜用同一组任务判断分工值不值

设计三类预约请求用于测量。最普通的一类只需读设备和场地。第二类场地先返回备用房间，因此需要知道房间编号才可读设备兼容性。第三类两个用户都试图占用最后一台相机，预览看起来一样。每类用同样的初始库存、模型和工具权限重跑，并分别记录串行单 Agent、可并行工具的单 Agent、两个独立查询 Agent 加协调者的结果。预算上限、计时起止和提交服务在三种配置里一致。要比较「多 Agent 体系贡献了多少」，先看强单 Agent 是否已能并行做独立工具查询。

正式对照也要说明系统预算怎样花。可以保留每次请求给各成员的输入和输出 Token、工具耗时和单项失败原因，再按原始请求合并统计。遇到一个分支超时，记录它是否触发重试、其他分支能否保留结果，以及从用户提交到拿到可用答复的时间。先锁定总调用预算，才看得出分工有没有让相同资源发挥不同作用。要考察更高资源上限，可以单独设一组实验，同时调高单 Agent 和多 Agent 的预算。查询结果相同而交接仍在重复转述时，查看每一跳是否引入了新事实或作出了必要决定。只有确认这些工作可以交给固定程序，才考虑省掉对应的一次模型调用。 [Agent 架构对照研究](https://arxiv.org/abs/2512.08296v3)

下面是用于手算的约定时间。解析用 1 秒，设备查 3 秒，场地查 5 秒，共同的汇总、确认与写入阶段合计 2 秒。多 Agent 版派发和验收各多 1 秒。这里忽略排队，而且各阶段总时长预先给定，数字不来自模型实测。请计算三种配置总用时，然后写出第二类请求的最长依赖路径和第三类请求的验收条件。

| 配置 | 第一类请求的计算 | 预期总用时 |
| --- | --- | --- |
| 单 Agent 串行查询 | 解析 + 设备 + 场地 + 后段 | 11 秒 |
| 单 Agent 并行工具 | 解析 + 两路查询中较长者 + 后段 | 8 秒 |
| 两个查询 Agent 加协调者 | 解析 + 派发 + 两路查询中较长者 + 验收 + 后段 | 10 秒 |

**核对结果**　第二类的路径依次经过解析、查场地、查兼容设备、汇总与提交。场地与设备两步存在依赖，在假定时长下这两步至少要 8 秒。团队可以并行准备与场地结果无关的事务，但不能把最关键的两项压成 5 秒。第三类应读最终库存和真实预约记录，核对两位用户的确认分别对应自己的预览，服务端最多为同一台设备的重叠时段创建 1 条有效预约。

如果实际测出多 Agent 版花得更久却改善了复杂请求的成功率，继续看改善来自哪种任务、花了多少额外调用、尾部延迟怎样变化，以及有无引入重复写入。报告里可以把三类任务的成功数、总消耗、拒绝的未授权提交和重复预约数分别列出。把分工保留在确有收益的路径，让成熟的简单路径继续用本来就稳定的实现。 [Stanford 第 8 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture08.pdf) · [Agent 架构对照研究](https://arxiv.org/abs/2512.08296v3)
