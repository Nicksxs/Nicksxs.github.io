用户说「查一下下周可以借的示波器」，应用可能要从中提取设备名、时间和动作，再决定查表还是追问。抽取失败有时表现为缺少字段，有时有完整的 JSON，日期却写成了下个月。要判断改提示、调采样、限制输出结构，还是给工具加校验，得先知道模型从输入到输出做了什么。这一讲把语言模型的几个环节串到同一次查询里，所有设备、输入与性能数值均为教学例子。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf) · [Stanford 课堂录像](https://youtu.be/Vr1NzH8bT44)

## 从字符到下一枚 Token

模型原始输入是一串 Token ID。分词器先把文本拆成模型词表能表示的单位，再把这些单位转换成数字。Token 和汉字、英文单词或字节没有固定的一一对应关系，字母、空格和常见词组可以被不同模型的分词器组合成不同的单位。测量长文档占用了多少输入预算，应用应尽可能使用服务实际使用的分词器或计费数据。用字数估算时要留出系统指令、工具说明、历史等实际也会传入的部分。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

自回归模型根据已经看到的序列给下一枚 Token 分配概率。对输出序列 `x₁, x₂, ..., xₙ`，联合概率可以按条件关系分解为 `P(x₁) × P(x₂ | x₁) × ... × P(xₙ | x₁...xₙ₋₁)`。实际生成通常已经有输入前缀，第一项也是在前缀给定时的选择。模型产生的每枚 Token 会接回前缀，再影响下一步。这能解释为什么开头把 `lookup` 选成 `reserve` 以后，接下来的字段也可能围绕预约展开。把所有步骤的概率直接相乘会得到很小的数，工程分析通常累加对数概率。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

理解这种分解还可以避免把「贪心」当成全局最优。比如第一步可选 `A` 和 `B`，概率分别为 0.6 和 0.4。`A` 后最好的下一步概率为 0.5，`B` 后最好的下一步概率为 0.95。直接挑 `A`，两步的最大联合概率为 0.3。保留 `B` 这条前缀，能得到 0.38。束搜索一类策略会同时保留若干前缀，再逐步筛掉较弱路径。它为探索可能的序列付出了额外计算，概率高的完整序列也不能保证代表正确业务动作。这里的数值来自手算。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

### 温度、top-k 和 top-p 怎样进入解码

网络末端给每个候选 Token 一个未归一化分数，常写成 logit。把每个分数除以温度 `T` 后做 softmax，得到 `pᵢ = exp(zᵢ / T) / Σⱼ exp(zⱼ / T)`。只看这一操作时，`T` 为正数。温度变小会放大分数差距，使原本概率最高的 Token 更集中。温度变大，尾部候选往往取得更多概率。服务里 `temperature=0` 一般约定为确定性的贪心行为或接近它的模式，公式里的除数仍应为正，实际细节由供应方定义。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

`top-k` 留下最高的 `k` 个候选。`top-p` 从高到低累加概率，保留累计概率首次达到或超过阈值的最短前缀，再在其中抽样。假设 5 个候选概率为 0.52、0.23、0.12、0.08、0.05。设置 `top-k=3` 会保留前三个。设置 `top-p=0.75` 会保留前两个，也包含使累计概率达到阈值的那个 Token。候选集里的概率要重新归一化。原始分布更平坦时，同一个 `top-p` 值可能保留更多词，直接调阈值不能控制回答长度。不同运行时也可能对多项过滤有不同顺序，比较前要核对实现。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf) · [Nucleus Sampling 论文](https://arxiv.org/abs/1904.09751)

预约助手如果只允许 `lookup`、`ask` 和 `reserve` 三种意图，先把动作词表和状态机约束好，再决定是否需要采样。简单抽取经常需要复现和可调试，可先把生成配置固定下来，用一批典型输入看结果。写摘要时，输出可以有多种说法，可以按事实和覆盖度检查。比较这两类表现要记录错误字段和服务器状态，单看模型回答更活泼还是更一致，不能判断哪种设置适用。

### 上下文是输入的一部分

模型每一步用前面的 Token 来估计后面会出现什么。对调用方来说，改变工具说明、给范例、更新当前日期、截掉一段历史，都会改变参与计算的前缀。示波器助手需要把「下周」换算成具体日期时，本地日期和时区尤其重要。把设备名称从 JSON 的 `instrument_name` 字段改成 `device`，会同时影响提示、接口、验证器和后面的工具调用。小改动最好带着相同请求做对照，确认模型输出和程序实际处理的含义一起发生了符合需求的变化。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf) · [Effective Context Engineering for AI Agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### 找到一次生成改变选择的位置

排查一个错误结构化调用，可以固定同一条消息并记录一次完整的输入和生成。假设模型第一项给出 `lookup`，却在日期上漏掉了周几。错误发生在选日期词元之前时，需要看有没有传相对日期和时区规则。格式里本来没有留某个字段时，应看工具契约。模型已经输出对的日期但应用解析错了，则回到代码验证。比起同时改系统提示、温度和模型名，一次只改变一个环节并保留相同任务集，更容易观察到哪些差异来自本次改动。

用解码检查举例，预约服务需要 `campus`，模型却时有时无。可以把输入文字固定，比较自由输出和受约束输出的结构缺失次数。之后先固定输出格式，再换三种语义相同的用户说法，测试地区别名能否落到同一个校区。前一个实验关注结构，后一个关注理解。给各自的失败单独计数，可以知道该做的是改契约、补样例还是增加验证。模型多次输出完全相同也不能证明业务上正确，需要拿真实目录或可核对的模拟数据验证。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

## 注意力、上下文长度和实际计算

现代自回归模型常使用 decoder-only Transformer。输入 ID 先转换成向量，并加入能区分位置的信息。在每一层里，注意力让当前 Token 利用前文，再用前馈网络变换表示。多头把不同的投影分开计算，残差和归一化帮助层间传递。一条预约语句里，「下周」出现在设备名称之前，相关日期描述可能在后来一轮消息里。注意力能把这些位置关联起来，应用仍应避免同时提供互相冲突的日期规则。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf) · [Transformer 论文](https://arxiv.org/abs/1706.03762)

### Q、K 和 V 的分工

如果把一层收到的表示写成矩阵 `X`，可以通过不同的权重得到 `Q=XW_Q`、`K=XW_K`、`V=XW_V`。对当前位置的 query 和各位置的 key 做点积，用 `√dₖ` 缩放，再做 softmax 得到分配在可见位置上的权重。用这些权重汇总 values，构成传到后面的新表示。一个简写是 `softmax(QKᵀ / √dₖ + mask) V`。因果遮罩让训练中的第 `t` 个位置看不到未来 Token。对一段完整序列做这一计算时，不同位置可以在硬件中并行，生成新文本仍必须等上一枚 Token 确定后再推进。 [Transformer 论文](https://arxiv.org/abs/1706.03762) · [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

比如在实现中，按 8 枚 Token 处理一个短输入，全注意力会计算不同位置之间的关系。长度翻倍后，位置对的数量接近原来的四倍。实际 GPU 代码可用分块和更有效的显存访问避免保存完整的注意力矩阵，但仍需区分算术量减少和中间内存减少。对于长任务，更适合从模型采用什么注意力、工具历史如何累积以及可获得的运行时指标判断开销。不要用一个固定阈值推断任何模型何时一定慢下来。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf) · [FlashAttention 论文](https://arxiv.org/abs/2205.14135)

### 线性注意力省掉了哪一部分

课程用线性注意力说明另一种计算路线。把相似度写成特征映射的内积后，可把逐个 query 与所有 key 的配对，改成先累计 key 和 value 的统计量，再用当前 query 读它。粗略地看，乘积可以改变结合次序。对自回归场景，前缀统计量也可随新 Token 更新。这样能让计算随序列长度按不同方式增长。普通 softmax 的逐行归一化和两两指数内积不能直接用同一个换序技巧一模一样地求出。具体模型需要采用合适的特征映射或其他注意力变体，这会影响能检索到的远程信息和对应的速度。混合模型在不同层选用不同方式，不能只根据产品写的最大上下文长度判断真实推理成本。 [线性注意力论文](https://arxiv.org/abs/2006.16236) · [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

### 把最大输入和实际有效上下文分开

部署时可以把上下文容量理解成硬上限。请求要给系统指令、工具定义、已发生的助手和工具消息，以及将生成的输出预留空间，具体约束以模型和服务环境为准。还要考虑另一项测试：在已经能接受的输入长度内，模型能不能找到需要的证据并据此行动。给两个请求同样总字数，一个把当前日期放在近处，一个把它埋在旧状态中，比较它们提取同一日期的表现。用可达的精确信息去测，比讨论门槛大小更能回答这个应用是否需要压缩或检索。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf) · [Lost in the Middle 论文](https://arxiv.org/abs/2307.03172)

### 隐藏状态与人看到的解释

注意力权重参与生成中间向量，最后的回复由多层计算共同产生。应用能观察到工具调用请求、答案和服务支持的有限指标，不宜直接把某个注意力头的权重或模型写出的理由当成完整的因果解释。比如助手把「下周」误读成当前周，哪怕生成一段说自己已查日历的理由，仍可以用请求里日期字段、程序可用的时区和工具日志做确定判断。这些信号的用途不同：模型解释便于理解行为，结构化踪迹便于验证某次真实执行。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf) · [Transformer 论文](https://arxiv.org/abs/1706.03762)

一个容易理解的计算是只看两个能进入注意力的位置，把它们的 value 当作二维向量。假设缩放后得分是 `ln(3)` 和 `0`，归一化权重是 `0.75` 和 `0.25`。若 value 分别为 `[2, 0]` 和 `[0, 4]`，加权结果为 `[1.5, 1.0]`。把第二个位置用遮罩去掉，权重全部落在第一个位置，结果变为 `[2, 0]`。这个手算说明为什么模型能混合多个位置的表示，也说明可见范围变化会改变同一位置得到的信息。真实模型的向量含义更复杂，没有一维直接对应「可借」这样的人类概念。

## 训练会影响模型学到哪些行为

训练阶段和应用阶段处理的是两个问题。训练改变参数，应用构造输入、选择工具并控制外部环境。预训练通常用大量文本做下一 Token 预测，可以把目标写成真实下一 Token 的负对数概率 `−log p(x_t | x_1,...,x_{t-1})`，在许多位置上聚合损失。后续可能用不同的数据配比继续训练，加长可处理的序列或强化一些能力。课程介绍这些阶段时强调数据、算力和目标的区别，不同模型的具体训练安排会变化。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

| 做法 | 典型训练信号 | 在工程里仍要检查什么 |
| --- | --- | --- |
| 预训练 | 文本中真实的下一项 | 模型会接写内容，当前设备状态仍需查服务 |
| 监督微调（SFT） | 人写或筛选后的指令和期望回复 | 给了字段示范以后，遇到缺少日期是否会追问 |
| 偏好训练 | 对同一输入的较优、较差输出 | 选择的偏好是否代表业务真正需要的行为 |
| 可验证奖励训练 | 由验证器产生的结果信号，如测试是否通过 | 验证器覆盖率够不够，有没有漏掉不该发生的副作用 |

常见 RLHF 流程可以先用偏好数据训练奖励模型，再根据奖励优化生成策略。标准 DPO 直接使用偏好对，把较优较差响应相对于参考策略的得分差写进目标，训练中无需另外拟合一个独立奖励模型。给预约助手训练时，高质量的样例可以展示如何向用户补问日期以及怎样看待否认写入的确认结果。用词礼貌、句子简短和确保无越权执行应各有可检验的条件，目标含糊时提供更多偏好数据也可能强化原本不希望出现的选择。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf) · [DPO 论文](https://arxiv.org/abs/2305.18290)

如果用工具轨迹继续训练，轨迹里要同时有模型请求、工具响应和环境变化，不能只收集最终答案。在一个状态固定的环境里，两条成功轨迹可能分别选了不同顺序完成任务。也可能有轨迹说得像成功，工具层却返回错误。先独立核验环境，再用模型输出构造训练或评测材料，才能区分这些情况。对复杂任务用一个终局信号做训练时，长路径里哪些选择应归功或归责也更难确定。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

### 从一组样本理解训练目标

假设预训练任务的真实下一枚 Token 是 `借`，模型给出的概率是 0.25，这一位置的负对数损失约为 1.386。如果概率变成 0.5，损失降到约 0.693。损失变小意味着模型在这个位置更看好目标，但不能据此断言它理解了所有预约约束。监督微调可以让模型在「学生问什么时候可借」时学习输出期望样式。格式规律在一些情况下能泛化到相近问句，涉及授权或当前库存时仍需让执行器访问环境。

偏好优化的一个例子是让同样的问题产生两种回复：一条在缺日期时追问，一条擅自默认下周一。样例标注要指出当前规则要求追问。如果把评价变成「是否礼貌」「有没有给答案」之类的模糊条件，错误日期也可能被偏好选中。对有可验证规则的任务，可以添加确定性的执行达标信号。给工具一个候选请求，验证返回状态、日期约束与是否发生写入。奖励或通过率提高以后，再回头看这套信号是否能被无意义地满足。例如校验器只要字段都非空就给分，填入错误日期也会过关。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf) · [DPO 论文](https://arxiv.org/abs/2305.18290)

对工具产品而言，可改变的变量比训练更多。可以调整输入里放哪些资料，选择一条更易验证的流程，或者让系统把权限、确定日期和环境状态交给普通程序处理。就算训练让模型更善于写结构化请求，执行成功仍有工具版本、稳定性和数据条件。把错误先归到「识别用户需求」「生成格式」「工具参数」「运行环境」四类，下次才有办法对照一项模型升级真正解决了哪类问题。

## 生成一次回答的耗时花在哪

输入进来以后，服务先处理已经确定的 Token，这个阶段常叫预填充（prefill）。如果执行的是标准注意力模型，处理提示时会为已有位置形成可供生成复用的 key 与 value。随后进入解码（decode），一次通常产生一枚新 Token。服务可以保存 K/V 缓存，后面的每一步就能利用已经处理过的位置，避免为所有历史重新计算这一部分。长输入会增加预填充工作量和缓存需求。输出的 Token 多，也会增加逐步推进的工作量。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

### 一份缓存量级的手算

对简单的单个序列、标准注意力 K/V 缓存，可以把每个 Token 的缓存大小估成 `层数 × 2 × KV 头数 × 每头维度 × 每元素字节数`。`2` 代表 K 和 V 各一份。若假设 24 层、8 个 KV 头、每头 128 维、每个元素 2 字节，每 Token 是 `24 × 2 × 8 × 128 × 2 = 98,304 bytes`，也就是 `96KiB`。8,192 枚 Token 对应约 `768MiB`。这是只算该份理论缓存的例子，实际还会受多请求、模型支持的注意力结构、分配策略和量化决定。改模型前先确认 KV 头数而不是仅看 query 头数。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

部署侧的时延可以从首 Token 延迟（TTFT）开始量，它包含请求到收到第一枚 Token 的时间。之后可算后续每 Token 的平均时间（TPOT），也可以记录 token/s。用户视角的首 Token 延迟还会受排队和传输影响，不能直接当成硬件完整预填充耗时。输出 100 枚 Token 的请求有 99 个相邻输出间隔，如果这部分的平均间隔是 20ms、TTFT 是 400ms，则从提交到收到末 Token 约为 `400 + 99 × 20 = 2,380ms`。多个请求同时跑时，所有请求合计的吞吐量与单个用户感受到的输出节奏也各自需要标明。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

### 把算力和内存带宽放进同一个判断

推理中，同一段大输入在预填充阶段可以并行参与计算，适合硬件一次处理较大的矩阵。逐 Token 生成时，单个请求每步新算的 Token 很少，反复读取模型参数和缓存往往变得显眼。把模型计算放到运行条件里考虑，才可以理解为什么有些测量中增加并发能提高总体吞吐，却让某个请求等得更久。硬件性能的分析常区分计算吞吐上限和内存带宽上限，具体瓶颈跟输入输出比例、批大小、缓存以及模型结构有关。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

选择哪项优化之前，先看业务里最受影响的是什么。如果单次请求要读数十页实验室说明才输出两句话，去掉不相关的输入可能比追求更高的逐 Token 速度更有效。如果工具说明很短，但模型每轮输出很多重复解释，结构化短响应或控制输出预算就更直接。若系统每次都要多轮调用，应该同时记每轮成分和整条任务总时间。省掉一次错误重试的效果，可能比优化其中一次小调用更明显。多轮工具结果如果被整块原样写回上下文，还要单独检查后续轮的输入是否不断增长。

### 缓存、投机解码与运行时预算

稳定的系统前缀有机会重复使用计算结果。例如工具规范和输出格式放在前面，用户的日期、文件内容及临时工具返回放在后面。在服务支持前缀缓存的条件下，两个请求只有共享的前段可能复用。把带当前时间的字段或随机标识塞到第一个消息的开头，可能让前缀从很早就分叉。要确定是否有收益，仍要比较实际服务报告的缓存命中和首 Token 延迟，并保持输入大小、地区和请求负载尽量一致。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

投机解码的典型做法是用较快的草稿模型提出一串候选，再让目标模型并行核验若干位置。接受多少候选，要看目标分布和验证规则。适当的接受与重采样方法可以保留目标模型的输出分布，加速来自减少等待目标模型逐枚推进的次数。如果草稿经常猜错、批量验证成本太高或现场配置不同，速度提升需要重新测。应用通常先看服务已经提供了什么，再用实际需求衡量，而不依赖「标注支持某项优化」推断任务效果。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf) · [Speculative Decoding 论文](https://arxiv.org/abs/2211.17192)

在分配更多推理预算时，还可以让模型多生成几份候选，再按规则或验证器选。把 5 个日期候选交给可解析日期校验器有所帮助的条件，是其中至少包含一个正确值、而且验证器能选出来。只验证了格式，5 个错误日期也能全部通过。写入类动作则要避免为比较候选而把每个候选都真实执行一次。可以先比较只读推导或草案，把能产生外部状态变化的动作留到确认证据已经齐全以后。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

### 多条候选怎样复用同一份验证器

多次采样可以用来覆盖更大的候选范围。设每个候选单独成功的概率是 `p`，且相互独立，采样 `k` 次至少有一次成功的概率为 `1−(1−p)^k`。例如 `p=0.5`、`k=3` 时得到 0.875。这个演算只描述候选集合，应用得找得到正确那项才会获益。真实模型多次犯错往往相关，概率也会随不同题目变动，不能拿这个公式直接预测整体成功率，更不能忽略额外开销。 [Repeated Sampling 论文](https://arxiv.org/abs/2407.21787) · [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

如果目的只是生成 `lookup` 请求，可以离线检查三个候选日期是否语义一致，以及是否落在用户给定的范围内。验证器确切知道校区和日期时，容易选出合格项。如果问题是「给一条合适的实验方案」，仅靠规则通常只能检查少数条件。此时可以比较候选的引用、起草理由和显式约束，再加人工验收样本。验证过程中应避免每条候选都对真实预约服务写入。只读检索、模拟环境或只生成草案提供了安全的比较位置。

## 用输出契约和上下文投影把例子接起来

可以把这次任务经过的字段写出来。工具执行器拿到 `intent`、`device` 和 `day`。`intent` 只允许 `lookup` 与 `ask`，`day` 没解析出具体日期时是 `null`。应用知道任务当天的日期和时区，也知道用户最新一条明确的日期。把关键资料靠近当前请求提供，别把过期排期当成资料传给模型。结构化输出的大致处理过程是先把模型的输出约束在可解析格式，再经过类型、业务和权限检查。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

约束解码可以在生成每一个 Token 时限制可选项。比如到 JSON 对象的键位置只允许本对象声明的键，在一个枚举值开始后，只允许把它补成合法选项。实现需要考虑一枚 Token 可能覆盖引号和多个字符。约束保证的范围取决于格式规则、分词和服务实现。设备编号是否来自用户、日期是否真的存在、谁能访问对应资源，仍要在结构检查后逐项核验。遇到输出被长度截断、模型拒答或服务超时，也应该允许返回明确错误，而不是默默猜一个默认值。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

| 输入或响应 | 可解析 | 业务检查 | 下一步 |
| --- | --- | --- | --- |
| `{"intent":"lookup","device":"OSC-01","day":"2026-09-30"}` | 是 | 日期存在，设备仍需查目录和授权 | 权限通过后只读查询 |
| `{"intent":"lookup","device":"OSC-01","day":"2026-09-31"}` | 是 | 日期不存在 | 让模型修正或向用户询问 |
| `{"intent":"ask","device":"OSC-01","day":null}` | 是 | 缺少具体日期，`ask` 分支合规 | 提一个澄清问题 |
| `{"intent":"lookup","device":"OSC-01"` | 否 | 输出在结尾前中断 | 记录异常，可按预算重试 |

程序可以缓存当前任务的结构化状态，在模型每轮输入里只投影有用的字段，例如「已经问过校区」「查过一个时段」「不能写入」。历史越来越长时还可以把细节留给检索工具。准备压缩前和压缩后两份输入时，选出需要保留的业务事实来回归。删除当前授权、用户最后一次日期更正或最新工具错误，即使减少了输入，也可能让后续动作改变。 [Effective Context Engineering for AI Agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) · [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

### 格式约束要精确到哪里

程序约定字段名和类型时，模型通常只看到一部分规则。比如 JSON 知道 `start` 与 `end` 是两个字符串，执行器还应确认它们来自同一时区，开始时间早于结束时间，预约不能超过实验室单次借用上限。如果模型服务能约束枚举和值的类型，可以让「只读」和「预约」变成清晰的选择。不同工具的业务限制不相同，一份供应方支持的 JSON Schema 子集，也不一定能表达全部业务约束。把格式规则放在接口里，把依赖当前用户、日期或状态的判断放在执行器里，就能逐项测试。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf)

实际输出还可能碰到重复键、极长字符串、无效日期或额外字段。很多 JSON 解析器会保留重复键的最后一个值，另一些会直接拒绝。假如 `device` 出现两次，上游日志记录的值与真正用于查询的值可能不一样。需要一致时可以在解析器里拒绝重复键。下面的测试程序只演示缺字段和日期校验。接入写入前可以为重复键准备专项用例，并把未知字段和格式错误反馈给运行层，不把预计中的格式当成已经核验的数据。 [JSON 标准 RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html)

任务的动作集合也会影响系统表现。假设执行器同时知道浏览目录、查排期、生成预约预览和确认写入四个操作。对于「查一下」这一个意图，当前回合可以只提供只读工具和追问入口。这样生成出来的语句天然处在缩小后的动作范围。对于下一回合明确要预约的请求，再根据权限和确定的时段开放预览。模型看到的动作规范与运行层实际允许的动作要一起更新。即使模型曾经看过旧工具列表，也应由执行器按最新规则检查。

### 给这条设备查询准备一份上下文

可以把固定规则、当前状态、临时用户消息和可查外部数据分别列成表。固定规则里有「只读查询不改变排期」「未得到具体日期就询问」。当前状态里有已经确认的设备及校区。用户消息里的「改成周五」需要覆盖之前的周四。外部数据里有最新设备资格、排期状态和维护记录。真正发给模型时，先放经常复用的规则，再放频繁变化的当前任务和必要证据。无需提前把所有工具都调一遍来填满上下文。 [第 2 讲课件](https://web.stanford.edu/class/cs329z/slides/lecture02.pdf) · [Effective Context Engineering for AI Agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

利用同一条用户问题设计两个版本。A 把整段聊天记录传进去，B 保留最新日期和已经确认的设备型号，并给出能查旧记录的入口。检查在设备名一模一样时，两个版本的工具参数是否一致。再加一个只存在历史里的重要约束，例如用户说过下午四点前，确认 B 把它保留下来。如果看到了输入变短但候选日期开始越界，就能定位压缩逻辑漏掉了哪类字段。挑选诊断样本时，专门准备一条反转前述事实的后来消息，验证系统优先使用用户最近确认的值。

## 练习一｜手算候选集，再让代码核对

使用 5 项示范分数，验证贪心选择、集合裁剪与概率重算。下面的代码只用标准库，返回的是分布，未运行模型。先手算 `top-p=0.75` 时保留几项，再看打印结果。真实推理引擎还要兼顾数值、采样和对硬件的批处理，这里只保留可独立核对的核心步骤。

```python
from math import exp, isclose, log


def distribution(scores, temperature=1.0, *, top_k=None, top_p=1.0):
    if not scores or temperature <= 0 or not 0 < top_p <= 1:
        raise ValueError("invalid sampling configuration")
    ranked = sorted(scores.items(), key=lambda item: (-item[1], item[0]))
    if top_k is not None:
        if top_k < 1:
            raise ValueError("top_k must be positive")
        ranked = ranked[:top_k]
    peak = ranked[0][1]
    weighted = [(label, exp((score - peak) / temperature))
                for label, score in ranked]
    total = sum(weight for _, weight in weighted)
    kept = []
    mass = 0.0
    for label, weight in weighted:
        kept.append((label, weight))
        mass += weight / total
        if top_p < 1.0 and mass >= top_p:
            break
    retained = sum(weight for _, weight in kept)
    return {label: weight / retained for label, weight in kept}


scores = {label: log(probability) for label, probability in [
    ("A", .52), ("B", .23), ("C", .12), ("D", .08), ("E", .05)
]}
base = distribution(scores)
pruned = distribution(scores, top_p=.75)
short = distribution(scores, top_k=3)
assert list(pruned) == ["A", "B"]
assert isclose(pruned["A"], .52 / .75)
assert list(short) == ["A", "B", "C"]
assert list(distribution({"A": 0, "B": -22})) == ["A", "B"]
assert distribution(scores, .5)["A"] > base["A"]
assert distribution(scores, 2.0)["A"] < base["A"]
for name, row in [("top_p", pruned), ("top_k", short)]:
    print(name, {label: round(value, 5) for label, value in row.items()})
```

预期 `top_p` 输出 `A=0.69333`、`B=0.30667`，`top_k` 保留前三项并重新归一化。把两个截断选项一起打开时，这段代码在 top-k 截断后重算分布，再按 top-p 保留候选。对照另一个采样器时应明确顺序，尤其是要复现实验而不仅是解释概念。贪心只取最大项，可以用 `max(scores, key=scores.get)` 单独算，其结果是 `A`。

## 练习二｜把合法 JSON 和能执行的请求分开

设备已经在固定名录里，测试本身只验证输入，不访问排期。下面这段代码用日期解析器核验日历日期，再按动作和日期决定进入查询还是追问。四个失败例子特意给到不同的退出状态。观察测试能否区分消息截断、字段不齐、日期不存在和设备已被移除。

```python
import json
import re
from datetime import date


DEVICES = {"OSC-01", "OSC-02"}


def check_request(raw):
    try:
        request = json.loads(raw)
    except json.JSONDecodeError:
        return "INVALID_JSON"
    wanted = {"intent", "device", "day"}
    if not isinstance(request, dict) or set(request) != wanted:
        return "INVALID_FIELDS"
    intent, device, day = (request[name] for name in ("intent", "device", "day"))
    if intent not in ("lookup", "ask") or not isinstance(device, str):
        return "INVALID_FIELDS"
    if device not in DEVICES:
        return "UNKNOWN_DEVICE"
    if day is None:
        return "ASK_DATE"
    if not isinstance(day, str) or re.fullmatch(r"[0-9]{4}-[0-9]{2}-[0-9]{2}", day) is None:
        return "INVALID_DATE"
    try:
        parsed = date.fromisoformat(day)
    except ValueError:
        return "INVALID_DATE"
    if intent == "ask":
        return "ASK_WITH_DATE"
    return f"READY:{device}/{parsed.isoformat()}"


cases = {
    '{"intent":"lookup","device":"OSC-01","day":"2026-09-30"}': "READY:OSC-01/2026-09-30",
    '{"intent":"lookup","device":"OSC-01","day":"2026-09-31"}': "INVALID_DATE",
    '{"intent":"ask","device":"OSC-01","day":null}': "ASK_DATE",
    '{"intent":"lookup","device":"OSC-01"': "INVALID_JSON",
    '{"intent":"lookup","device":"OSC-01"}': "INVALID_FIELDS",
    '{"intent":"lookup","device":"OSC-99","day":"2026-09-30"}': "UNKNOWN_DEVICE",
}
for raw, expected in cases.items():
    state = check_request(raw)
    assert state == expected
    print(state)
```

只有第一条返回 `READY:OSC-01/2026-09-30`，下一步才具备从工具层检查权限并发起查询的条件。第 2 条是合法 JSON，也过得了字符串格式检查，具体日期仍不存在。第 3 条已经按约定把缺项传回程序。想把例子扩展到理解日期是否符合用户原话，可以给定当前日期与「下周」的用户描述，检查解析结果确实位于相应的日期范围。已经通过结构校验的错误业务值才是这一步要发现的失败。

### 练习三｜一段生成是哪里慢

给两条固定记录。A 的 TTFT 为 650ms，末 Token 到达时间为 1,550ms，共 46 个输出 Token。B 的 TTFT 为 300ms，末 Token 到达时间为 1,680ms，共 47 个输出 Token。这组是手算示例。A 的生成间隔平均 `900 / 45 = 20ms`，B 的平均 `1,380 / 46 = 30ms`。A 开始得慢，后续更快，结束也更早。只看首字会挑 B，只看总时长会挑 A。再加同一请求的输入大小、缓存命中和不同并发量，才能判断是否有理由把某一项差异归因到预填充或解码。实际跑评测时可对固定请求记录多次结果，分别报告分位数和失败样本，保留时间测量的起止口径。


### 练习四｜给上下文改动写一条回归测试

假设聊天记录有下面 4 条，助手要生成下一次查询的参数。

| 消息 | 内容 | 最小工作视图里怎么处理 |
| --- | --- | --- |
| 用户 1 | 周四想借北校区的示波器 | 保存设备和目标校区，周四暂存为旧值 |
| 工具 1 | OSC-01 周四满员 | 保留已经查过的时段和结果 |
| 用户 2 | 那改周五，我四点之前得还回去 | 把目标日改为周五，补上归还上限 |
| 助手 1 | 可以，我先查北校区 | 省掉礼貌回复，避免把它误当已执行事实 |

预期工具收到 `campus=north`、`device=OSC-01`、`day=Friday` 和单独的 `return_before=16:00`。如果验证器把 `return_before` 解释成「预约开始时间必须早于」，15:30 开始且借一小时的选项仍可能通过。本例约定「之前」为严格早于。加入三个固定候选，分别在 15:45、16:00 和 16:30 结束，只有第一个符合归还条件。有效断言还需检查日期与设备，及结束时间严格早于 16:00。

把这组数据分别送给保留全部消息和投影后只保留必要状态的两版代码。可以把结果按三个层次记录：日期和校区是否与用户意图一致，候选是否符合归还条件，模型输出中有无声称已经预约。这里的期望输出可以手动核对。测量时重新数实际输入 Token、是否调用工具和完成时间，别把缩短文本与加快响应直接画等号。


### 练习五｜区分模型能力和服务配置

实验室助手收到「下周一以后、周三之前能借到 OSC-01 吗」。想判断换了供应服务是否改善结果，可以把一次评测分三轮。第一轮不给模型调参，只将同样的用户原话、时区、当前日期和工具规范发给两个服务，分别检查其输出是否落在允许日期集合。第二轮固定服务，比较完整历史与缩短后的上下文，记录丢失的字段和输入大小。第三轮把正确的业务字段直接送进同一个模拟工具，确认排期接口确实会按照传入的日期工作。第一轮出现偏差可能跟模型、格式支持、采样等多个因素有关，第三轮则能单独确认执行器有没有解释错。

本例可以把含糊的「以后」和「之前」作为需要澄清的条件，或者在测试前选定明确的产品约定。例如约定两端都不包含，则只接受下周二。下周一或周三形式合法，但按约定都应失败。设计这份评测时应把当前日期持久化，到了下一周重跑仍应得到相同的星期范围。结果要记录输入和输出 Token、延迟字段的单位、工具结果与任务是否完成。之后再决定运行配置中改的是什么，避免把测试环境变化误算作模型提升。
